# Verify the Compute Provider

A RISC Zero proof shows which guest program ran and what it committed. This page explains how the
Interfold contract checks that proof, which values each check binds, and how to confirm the image ID
of a deployment. It is for E3 program developers, auditors, and operators who did not build the
deployment. At the end, you can tie a deployed verifier to a source commit.

## Two checks on one proof

`publishCiphertextOutput` checks the compute proof two times, in this order
(`InterfoldLifecycle.publishCiphertext` and `_isValidCiphertextHash`):

1. The protocol ciphertext verifier of the encryption scheme. For BFV this is
   `Risc0BfvCiphertextVerifier` (`contracts/verifiers/bfv/Risc0BfvCiphertextVerifier.sol`).
2. `verify` on the program contract of the E3.

Before these checks, the Interfold contract calls `verifyDataAvailability` on the program contract.
If a verifier returns `false`, the call reverts with `InvalidOutput`. After the program check, the
Interfold contract reads the stage again and checks committee viability again. Then it stores the
output hash and commitment and moves the E3 to `CiphertextReady`.

Both verifiers rebuild the same journal and call the RISC Zero verifier:

```solidity
risc0Verifier.verify(proof.seal, imageId, sha256(journal));
```

The RISC Zero verifier reverts when the seal does not prove that the guest with `imageId` committed
that journal.

## What each check binds

The journal has nine 32-byte fields (`lib/Risc0ComputeProof.sol`). The table shows where each
verifier gets each field. A call argument is a value from the caller of `publishCiphertextOutput`.

| Field                     | `Risc0BfvCiphertextVerifier`               | `MyProgram.verify` (template)                            |
| ------------------------- | ------------------------------------------ | -------------------------------------------------------- |
| Chain ID                  | `block.chainid`                            | `block.chainid`                                          |
| Interfold contract        | `msg.sender` (the Interfold proxy)         | `address(interfold)`                                     |
| E3 ID                     | Call argument                              | Call argument                                            |
| Encryption scheme ID      | `e3.encryptionSchemeId`                    | `e3.encryptionSchemeId`                                  |
| Committee public key hash | `e3.committeePublicKey`                    | `e3.committeePublicKey`                                  |
| Output ciphertext hash    | Call argument                              | Call argument                                            |
| Output SAFE commitment    | Call argument                              | Call argument                                            |
| BFV parameter hash        | Request-time hash, compared with the proof | Hash that `validate` stored, compared with the proof     |
| Input root                | **Proof** (not checked)                    | Root of the on-chain input tree, compared with the proof |

The caller supplies the output hash and the commitment, and the Interfold contract stores them in
the E3. The proof binds them to this chain, this Interfold contract, this E3, this committee key,
and these parameters. The prover cannot change these other fields.

<Callout type='error'>
  The protocol verifier does not check the input root. The program contract must compare the input
  root in the proof with its own tree root. If it does not, a prover can publish an output that it
  computed over inputs that nobody submitted. `MyProgram.verify` and `CRISPProgram.verify` both make
  this comparison.
</Callout>

The guest derives the input root from the ciphertexts it processes. `ComputeInput` has no root field
(`crates/compute-provider/src/compute_input.rs`). The root in the journal is therefore a function of
the inputs that the output used.

## The verifier is fixed for each E3

These properties hold without any action from you:

- **The verifier is fixed at request time.** `bindCryptoConfig` copies the current ciphertext
  verifier of the scheme and the parameter hash into a per-E3 record. A later
  `setCiphertextVerifier` changes only future requests.
- **The image ID cannot change.** `Risc0BfvCiphertextVerifier.imageId` and `risc0Verifier` are
  `immutable` and `public`. The constructor refuses a zero image ID and a verifier address with no
  code.
- **One verifier for each scheme.** The Interfold contract keeps one current ciphertext verifier for
  each encryption scheme. Every BFV E3 program on a deployment must use the guest that it names.

An E3 program can keep its own image ID and RISC Zero verifier. The template sets them in the
constructor and has no setter. `CRISPProgram` has `setImageId` and `setRisc0Verifier`, which only
its owner can call. A change to these values cannot replace an output that the Interfold contract
already accepted. It can make an E3 in progress fail, because `verify` then checks the proof against
a different guest.

## Check a deployment

Use this procedure to compare a deployed verifier with the released source. You need Foundry
(`cast`), an RPC URL, and the Interfold contract address from
[Contract Addresses](/reference/contracts).

<Steps>

### Read the verifier address

```bash
cast call <INTERFOLD_ADDRESS> "getCiphertextVerifier(bytes32)(address)" \
  $(cast keccak "fhe.rs:BFV") --rpc-url <RPC_URL>
```

The result is the ciphertext verifier for new BFV requests.

### Read the image ID

```bash
cast call <VERIFIER_ADDRESS> "imageId()(bytes32)" --rpc-url <RPC_URL>
```

### Read the RISC Zero verifier

```bash
cast call <VERIFIER_ADDRESS> "risc0Verifier()(address)" --rpc-url <RPC_URL>
```

Make sure that this address is the RISC Zero verifier that you expect for this chain.

### Compare with the source

Open `crates/support/contracts/ImageID.sol` at the release tag. Compare `PROGRAM_ID` with the image
ID from the chain. The two values must be equal. If they are different, the deployment does not
match this source.

### Check the program contract

Read `imageId()` on the program contract. Read `verifier()` on a template program or
`risc0Verifier()` on `CRISPProgram`. Compare them with the values from the previous steps.

### Generate the provenance manifest

From the repository root, run:

```bash
pnpm provenance:manifest --rpc <RPC_URL> --verifier <VERIFIER_ADDRESS> --out manifest.json
```

Make sure that the manifest shows `"complete": true`. The `unresolved` list names each field that
the script did not resolve.

</Steps>

The manifest (`scripts/generate-provenance-manifest.ts`) records these values:

- The source commit, and whether the working tree is clean
- The RISC Zero version, the guest toolchain, the host toolchain, and the guest builder image tag
  and digest
- The Interfold revision pins of the guest workspace, and the digests of the two lockfiles
- The guest ELF path and SHA-256, and the image ID from `ImageID.sol`
- The chain ID, the verifier address and the SHA-256 of its code, the RISC Zero verifier address,
  and the on-chain image ID

The manifest is `complete: false` when a field is missing, or when the on-chain image ID is not
equal to `ImageID.sol`. An incomplete manifest records an unfinished check. It is not a passing
result.

## Reproduce the image ID from source

The manifest compares the chain with the committed `ImageID.sol`. It does not rebuild the guest. To
check that `ImageID.sol` matches the source, rebuild the guest in the pinned Docker builder.

1. Check out the release tag.
2. Go to `crates/support`.
3. Run `RISC0_USE_DOCKER=1 cargo build --locked -p methods`.
4. Run `git diff contracts/ImageID.sol`. The diff must be empty.

Only the Docker build writes `ImageID.sol` (`crates/support/methods/build.rs`). A native build can
give a different image ID on a different toolchain, so the build script skips the Solidity output
for it.

The guest reads `e3-compute-provider` and `e3-fhe-params` through git revision pins. Three pins must
name the same revision: `e3-fhe-params` and `e3-compute-provider` in `crates/support/Cargo.toml`,
and `e3-compute-provider` in `crates/support/methods/guest/Cargo.toml`. A new revision gives a new
image ID, so a guest change needs a new `Risc0BfvCiphertextVerifier`.

<Callout type='info'>
  The SHA-256 of the ELF is not the image ID. SHA-256 checks that a file arrived intact. The RISC
  Zero image ID comes from the loaded memory image. The manifest records both values for these two
  different purposes.
</Callout>

## Limits of these checks

- **Proxy upgrades.** The Interfold contract is an upgradeable proxy. The per-E3 verifier record
  protects an E3 from `setCiphertextVerifier`. It does not protect against an upgrade of the proxy.
  That control belongs to [governance](/governance).
- **Program values.** The protocol verifier and each program contract keep separate values. The
  procedure above reads both.
- **Local mocks.** The template deploys `MockRISC0Verifier`, which accepts every seal. Its dev
  runner returns a placeholder seal. A local E3 therefore proves nothing about the computation.
