# Ciphernode Requirements

This page lists what a host needs to run a ciphernode. It is for operators who plan a new node or
size a server. Some limits are enforced by the node code, and this page says so. Other numbers are
guidance from earlier deployments, and the node does not check them. At the end, you can choose a
host and open the correct ports.

## Hardware

A ciphernode runs threshold cryptography and makes zero-knowledge proofs. The work uses a lot of CPU
and memory during DKG and proof generation. Memory is the only hardware value that the node checks.

| Resource | Enforced by the node                                                                                  | Guidance (not enforced)                                           |
| -------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Memory   | On Linux, the node does not start with less than 17 GiB. The default of two prover jobs needs 30 GiB. | 32 GB for mainnet.                                                |
| CPU      | No minimum. The node keeps `multithread_reserve_threads` (default `2`) logical CPUs for other work.   | 8 or more modern x86-64 cores for mainnet. 4 or more for testnet. |
| Disk     | No minimum.                                                                                           | SSD. Start with 100 GB for testnet and 500 GB NVMe for mainnet.   |
| Network  | One inbound UDP port for QUIC.                                                                        | A stable, low-latency connection that does not filter UDP.        |

### How the node sizes its prover work

The node runs CPU-heavy jobs (zero-knowledge proofs and threshold BFV work) in a shared pool. The
number of concurrent jobs is the smallest of three values:

- The requested value, `node.multithread_concurrent_jobs` (default `2`).
- The number of logical CPUs minus `node.multithread_reserve_threads` (default `2`).
- The memory limit: one job for each 13 GiB after a 4 GiB reserve for the node and the host.

On Linux, the node reads the host memory (`MemTotal` in `/proc/meminfo`) and the cgroup memory
limit, and it uses the smaller value. A container memory limit is a cgroup limit. When the result is
lower than the requested value, the node logs
`Reduced compute concurrency to fit detected CPU and memory limits`.

| Detected memory limit      | Prover jobs that the node admits |
| -------------------------- | -------------------------------- |
| Less than 17 GiB           | None. The node does not start.   |
| 17 GiB to less than 30 GiB | 1                                |
| 30 GiB or more             | 2 (the default request)          |

When the memory limit is too small for one job, startup stops with this error:

```text
the detected memory limit cannot safely run one prover job in addition to the node; increase the host or cgroup memory limit
```

The node never admits more jobs than the memory limit allows, also when you set a higher
`multithread_concurrent_jobs`. You can set the value in the configuration file or with the
`E3_NODE__MULTITHREAD_CONCURRENT_JOBS` environment variable.

### When a proof job fails

The node retries a failed proof job or key-share job. The wait between attempts is 5 s, 15 s, 60 s,
and then 300 s for each later attempt. From the second attempt, proof jobs run Barretenberg in
low-memory mode (`--slow_low_memory`). The node stops the retries when the E3 reaches a terminal
stage. The warning `Compute worker failed; automatic recovery remains active` does not mean that the
E3 failed.

## Operating systems and platforms

Each release publishes two `interfold` binaries and one Docker image. Other platforms must build the
CLI from source.

| Platform               | Release binary                  | Docker image (`ghcr.io/theinterfold/ciphernode`) |
| ---------------------- | ------------------------------- | ------------------------------------------------ |
| Linux x86-64           | Yes (`interfold-linux-x86_64`)  | Yes (`linux/amd64`)                              |
| macOS on Apple silicon | Yes (`interfold-macos-aarch64`) | Only with x86-64 emulation                       |
| Linux on ARM (aarch64) | No. Build from source.          | Only with x86-64 emulation                       |
| macOS on Intel         | No. Build from source.          | Yes (`linux/amd64`)                              |
| Windows                | No. Use WSL 2 (Linux x86-64).   | Yes, with Docker Desktop on x86-64               |

The memory check reads Linux interfaces. On macOS, the node does not detect a memory limit, so the
check does not stop startup. To build from source, use the Rust toolchain in `rust-toolchain.toml`
(Rust 1.91.1). The DAppNode package is built for `linux/amd64`.

## Network ports

| Port             | Protocol | Bind address | Purpose                                                         | Open to the internet |
| ---------------- | -------- | ------------ | --------------------------------------------------------------- | -------------------- |
| `9091` (default) | UDP      | `0.0.0.0`    | QUIC transport for libp2p. Set with `node.quic_port`.           | Yes, inbound         |
| `50505`          | TCP      | `127.0.0.1`  | Local control port for CLI commands. Set with `node.ctrl_port`. | No                   |
| Not set          | TCP      | `127.0.0.1`  | Optional node dashboard. Set with `node.dashboard_port`.        | No                   |

The DAppNode package uses UDP port `37173` for QUIC. Cloud firewalls (for example, AWS security
groups or GCP firewall rules) must allow inbound UDP on the QUIC port. Behind NAT, forward the same
UDP port to the host.

<Callout type='warning'>
  The control port accepts CLI commands for the running node. The node binds it to `127.0.0.1`. Do
  not forward or publish it.
</Callout>

The node finds its first peers through a DNS bootstrap address for its network:
`/dnsaddr/bootstrap.interfold.network` on mainnet and `/dnsaddr/bootstrap-sepolia.interfold.network`
on Sepolia. See [Run a Ciphernode](/operate/running#networking) to set peers.

## RPC endpoints

A ciphernode needs two endpoints for each chain:

- An Ethereum endpoint with a WebSocket URL (`ws://` or `wss://`). The node subscribes to contract
  logs with `eth_subscribe`. The endpoint must keep the log history from the contract deploy blocks.
- An Avail HTTP endpoint (`http://` or `https://`) for data availability. The node refuses to start
  when a chain has no `data_availability` entry.

An endpoint that dropped old logs can return an empty result without an error. Test your Ethereum
endpoint on [RPC Endpoints](/operate/rpc-endpoints) before the first sync.

## Disk and storage

The node keeps its state in a `.interfold` directory next to its configuration file. Run
`interfold config get db_file` to print the exact path.

| Path under `.interfold/` | Contents                                                                 |
| ------------------------ | ------------------------------------------------------------------------ |
| `config/<name>/key`      | The file that holds the encryption password for the local key store.     |
| `data/<name>/db`         | The key/value store, with the encrypted wallet key and libp2p key.       |
| `data/<name>/log.*`      | The append-only event log, with its `event-blobs-v1` directory.          |
| `noir/`                  | The Barretenberg binary, circuit artifacts, and prover work directories. |

`<name>` is the node profile name. The default profile is `_default`. The `data_dir` and
`config_dir` keys move the data and key directories.

Disk use grows with the E3 history that the node keeps. Events up to 32 MiB stay inside the event
log. A larger local event, for example a proof work plan, goes to a separate file in
`event-blobs-v1`. Each blob file is limited to 512 MiB. The node checks the length and SHA-256 hash
of each blob when it reads it.

At startup, the node deletes only blob files that no committed event references. Blob files that the
event log references stay on disk, also after their E3 completes.

<Callout type='warning'>
  Do not delete files in `event-blobs-v1` to free space. The event history that refers to them
  becomes unreadable. Expand the volume instead.
</Callout>

The disk values in the hardware table are first allocations, not retention estimates. Monitor free
space and growth for each E3, and expand the volume before it is full. Back up the complete
`.interfold` directory as one unit. Use SSD storage, because slow disk access can make the node miss
protocol windows. [Migrate a Node](/operate/migrating) explains how to move this directory.

## Check resource use

The [node dashboard](/operate/dashboard) shows node health. On a Linux host, these commands show the
system resources:

```bash
# Memory
free -h

# CPU and memory for each process
htop

# Free disk space
df -h

# The QUIC listener (UDP). Replace 9091 if you changed node.quic_port.
ss -ulnp | grep 9091
```
