# Node Dashboard

The Interfold has two dashboards. The local status page runs inside your ciphernode process and
shows what that node knows. The hosted dashboard is a public web app that reads the chain. This page
is for operators who monitor a ciphernode. At the end, you can turn on the status page and open it
safely from another computer, and you know when to use the hosted dashboard.

| Dashboard        | Where it runs                                    | Data source                                         | Use it to                                                                       |
| ---------------- | ------------------------------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------- |
| Status page      | In the `interfold start` process, on `127.0.0.1` | The state of the node, its peers, and what it noted | Check peers, the chain position, activation, and the E3s the node holds         |
| Hosted dashboard | `https://dashboard.theinterfold.com`             | Contract events and views of one network            | Inspect any E3, watch CRISP polls, and set up an operator from a browser wallet |

## Local status page

The `interfold` binary includes the status page. It needs no separate installation. It is off until
you set a port.

<Steps>

### Set the port

Add `dashboard_port` to the node definition in the configuration file. For the default node, use the
`node` key:

```yaml
# interfold.config.yaml
node:
  dashboard_port: 9092
```

For a named node, set the key under `nodes.<name>`. Select a free port. The default `quic_port` is
9091 and the default `ctrl_port` is 50505.

To set the port with an environment variable, use `E3_NODE__DASHBOARD_PORT=9092`. For a named node,
use `E3_NODES__<NAME>__DASHBOARD_PORT`.

### Restart the node

Stop the node, then start it again. The log shows this line:

```text
node status at http://127.0.0.1:9092
```

If the port is in use, the node logs a warning and runs without the page.

### Open the page

The page has no login and only reads. It binds to `127.0.0.1`, so open it on the host of the node.
From another computer, use an SSH tunnel:

```bash
ssh -L 9092:127.0.0.1:9092 <user>@<node-host>
```

Then open `http://127.0.0.1:9092`. Do not publish the port to a network.

</Steps>

### What the page shows

The page reloads every five seconds.

| Part               | Meaning                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Operator and chain | The operator address, the chain, and the block the node has read to, of the newest it knows.                       |
| Peers connected    | The peers the node has a connection to now.                                                                        |
| Active             | Whether the operator is active on the chain, as the logs the node has read say.                                    |
| Listed             | Whether the ciphernode registry lists the operator. An operator that is not listed cannot submit tickets.          |
| E3s                | Each E3 the node holds, its stage, and what the node would give up if its state were deleted.                      |
| Recent notes       | DKG failures, Ready reports, accepted rosters, and proofs that failed. `interfold node events` prints all of them. |

Before you stop a node for an update, check that the page shows no E3 that still owes work.

`GET /status.json` returns the same values for a monitoring system. See
[Status page JSON](/reference/dashboard-api).

## Hosted dashboard

The hosted dashboard at `https://dashboard.theinterfold.com` reads contract events and views
directly from the chain. It does not connect to your ciphernode, so it cannot show peers, logs, or
the local state of your node. Each page reads one network, and the page shows the network name. The
`VITE_NETWORK_HOSTS` build variable maps each domain to a network (`sepolia` or `mainnet`). Other
hosts use the `VITE_NETWORK` build variable, default `sepolia`.

It has three views:

| View                 | Link                                                        | What it shows                                                                                                                                 |
| -------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **E3 inspector**     | `#inspector`                                                | Each E3 on the network: request, committee, key generation, input window, compute, decryption, publication, failure, fees, and the event log. |
| **CRISP**            | `#crisp`                                                    | The CRISP polls of the network and their stages. The view only shows data.                                                                    |
| **Run a ciphernode** | [`#operator`](https://dashboard.theinterfold.com/#operator) | An interactive operator guide that sends transactions from a browser wallet.                                                                  |

The operator guide is the only view that writes to the chain. It reads the bond size, the ticket
price, the minimum ticket count, and the exit delay from `BondingRegistry`. It has five steps:

1. **Connect a wallet.**
2. **Authorize the bond owner.** The operator key sends `setBondOwner`.
3. **Bond the ciphernode bond.** The bond owner approves FOLD and sends `bondCiphernodeFor`.
4. **Register the ciphernode.** The bond owner sends `registerOperatorFor`.
5. **Buy tickets.** The bond owner approves the ticket collateral and sends `addTicketBalanceFor`.

After setup, **Manage the position** sends the other transactions of the `interfold ciphernode`
commands: `refreshOperatorStatus` (refresh the status), `removeTicketBalanceFor` (burn tickets),
`unbondCiphernodeFor` (unbond FOLD), `deregisterOperatorFor` (leave the network), `claimExitsFor`
(claim exits), `proposeBondOwner`, and `acceptBondOwner`. It shows the collateral in the exit queue
and the part whose exit delay has ended. An open slash proposal, or a committee of the operator that
is not released yet, can still hold a claim. The bond owner sends each of them, except that the
operator key can also deregister, any wallet can refresh the status and claim tickets, and the
proposed owner accepts a transfer. A node that runs without the CLI, for example a DAppNode package,
uses these actions.

**E3 rewards**, at the top of the page, shows the amount that the operator's recipient can claim and
a **Claim rewards** action. The recipient is the bond owner of the operator at committee
finalization, or the operator key when it had no bond owner. Connect the recipient wallet to claim.
The action sends `claimRewards(e3Ids)` for the completed E3s, then
`claimHonestNodeReward(e3Id, operator)` for each failed E3. Below it, the committee history shows
each E3 that selected the operator, with its outcome, its amount, and a claim status: In progress,
Claimable, Claimed, On hold (an open expulsion proposal holds the payment), Forfeited (an executed
expulsion), Needs processing, Not eligible (not an honest member of a failed E3), or No reward.
Point to a status to see its reason. A failed E3 needs `processE3Failure(e3Id)` before its honest
members can claim. Any connected wallet can send it with **Process** in the history.

The guide simulates each transaction before the wallet prompt, so a contract error, for example
`NotBondOwner`, shows before you sign. The guide manages the on-chain position only. The ciphernode
must run with the same operator key. See [Registration](/operate/registration) for the CLI
procedure.
