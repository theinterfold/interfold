# Run a Ciphernode

This page shows three ways to install and start a ciphernode: DAppNode, the `interfold` CLI, and
Docker. It is for operators who have a host that meets the [requirements](/operate/requirements). At
the end, the node runs, syncs the contract history, and waits for
[registration](/operate/registration). For a release change, follow [Upgrades](/operate/upgrades).

## Before you start

Prepare these items before you install the node:

- A host that meets the [requirements](/operate/requirements), with the QUIC UDP port open.
- An Ethereum WebSocket endpoint that keeps the full log history. Test it on
  [RPC Endpoints](/operate/rpc-endpoints) first.
- An Avail HTTP endpoint for data availability. The examples on this page use the defaults of the
  DAppNode package.
- An operator key: a dedicated Ethereum private key for this node. The node signs ticket submissions
  and release acknowledgments with it, so it needs ETH for gas.
- A bond owner wallet or Safe that holds the FOLD and the ticket collateral. A wallet that is
  separate from the operator key is recommended. See
  [Registration & Bonding](/operate/registration).

Use a fixed release version on an operator node. Do not use a moving version such as the `latest`
Docker tag.

## Choose a method

| Method   | Best for                                | Configuration                                   | Where the state lives                  |
| -------- | --------------------------------------- | ----------------------------------------------- | -------------------------------------- |
| DAppNode | A DAppNode box with a setup form        | The setup wizard renders `/data/config.yaml`.   | The `ciphernode_data` volume (`/data`) |
| CLI      | A Linux or macOS server that you manage | You write `interfold.config.yaml`.              | `.interfold/` next to the config file  |
| Docker   | Container hosts (Linux x86-64)          | You write `config.yaml` and mount it read-only. | A named Docker volume                  |

The CLI and Docker methods use the same configuration file. Write it first, as shown in the next
section. The DAppNode package writes its own file from the wizard values.

## Write the configuration file

The configuration file sets the node profile and one entry for each chain. Copy the example for your
network and replace the placeholders. The addresses come from the deployment manifest. See
[Contract addresses](/operate#contract-addresses).

The node applies these rules when it loads the file:

- Every enabled chain must belong to the `node.network` profile. `chain_id: 1` belongs to `mainnet`
  and `chain_id: 11155111` belongs to `sepolia`. One node serves one network. To keep an entry for
  another network in the file, set `enabled: false` on it.
- Each enabled entry must be a different chain. The node refuses to start when two enabled entries
  resolve to the same chain ID.
- Each contract must have a nonzero `deploy_block` when `rpc_url` is not a local address. Otherwise,
  startup stops with
  `Misconfiguration: Attempted to query historical events from genesis on a non-local node`.
- A ciphernode needs `interfold`, `ciphernode_registry`, `bonding_registry`, `slashing_manager`, and
  a `data_availability` entry on each enabled chain. The node refuses to start without them.
- Each `$NAME` or `${NAME}` in the file is replaced with the value of that environment variable. Use
  this to keep an API key out of the file, for example
  `rpc_url: 'wss://example.invalid/v2/${RPC_API_KEY}'`.

Keep the chain `name` as `mainnet` or `sepolia`. The `interfold config check` command matches chains
to the manifest by name, and it skips other names. Also set `chain_id`, because `config check`
compares it with the manifest. The command does not query the endpoint.

<Callout type='info'>
  The first sync starts at the lowest `deploy_block` of all configured contracts. On mainnet, the
  `fee_token` deploy block (20663730) is about 4.8 million blocks before the `bonding_registry`
  deploy block (25473398). The node does not use `fee_token`, so you can remove that entry to
  shorten the first sync. `interfold config check` then prints a note for it, but the check passes.
</Callout>

### Main configuration keys

The keys below matter most on an operator node. The
[Configuration Reference](/reference/configuration#node-keys) lists every node key, and
[Chain keys](/reference/configuration#chain-keys) lists every chain key.

| Key (under `node:`)           | Default                       | Meaning                                                                                         |
| ----------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------- |
| `network`                     | Inferred from the chains      | P2P profile: `mainnet`, `sepolia`, or `local`.                                                  |
| `quic_port`                   | `9091`                        | UDP port of the QUIC listener.                                                                  |
| `peers`                       | Empty (profile DNS bootstrap) | libp2p addresses to dial. See [Networking](#networking).                                        |
| `multithread_concurrent_jobs` | `2`                           | Requested prover jobs. The node lowers it to fit memory.                                        |
| `startup_timeout_secs`        | `1800`                        | Time limit for startup and the first sync. After it, the node exits with an error.              |
| `autowallet`                  | `false`                       | `true` generates a random wallet when none is stored. That key is not your registered operator. |

| Key (under each `chains:` entry) | Default  | Meaning                                                                                                   |
| -------------------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `rpc_url`                        | Required | WebSocket URL (`ws://` or `wss://`). The node needs it for log subscriptions.                             |
| `rpc_auth`                       | No auth  | `Basic` or `Bearer` credentials. See [RPC authentication](/reference/configuration#rpc-authentication).   |
| `data_availability`              | Required | `mode: avail` and an HTTP `rpc_url`. See [Data availability](/reference/configuration#data-availability). |
| `ingestion_confirmations`        | `1`      | Confirmations before the node applies a log.                                                              |
| `rpc_poll_interval_ms`           | `7000`   | Milliseconds between the polls of an HTTP provider for a receipt or a new block.                          |
| `rpc_log_range_blocks`           | `10000`  | Widest block range of one `eth_getLogs` request. See [RPC endpoints](/operate/rpc-endpoints).             |
| `enabled`                        | `true`   | `false` makes the node ignore the entry.                                                                  |

The defaults of one confirmation and a 7-second poll interval also apply when `rpc_url` uses
`localhost` or `127.0.0.1`, because that URL can be a proxy to a live chain. Set
`ingestion_confirmations: 0` and `rpc_poll_interval_ms: 250` only on a single-process development
chain such as Anvil. Do not set them on mainnet or Sepolia.

The `autonetkey` key has no effect in this release. The node derives its libp2p key from the wallet
key.

## Start the node

<Tabs items={['DAppNode', 'CLI', 'Docker']}>
  <Tabs.Tab unmount={false}>

The DAppNode package wraps the released `interfold` binary. Its setup wizard collects the values,
renders `/data/config.yaml`, stores the credentials, and runs `interfold start`.

<Steps>

### Install the package

Open the DAppNode UI (`http://my.dappnode`) and search the DAppStore for **Interfold Ciphernode**.
If the package is not listed, open **Installer** and use **Install from IPFS hash** with the hash of
a published release.

### Prepare the credentials file

Create a JSON file with exactly these two fields. The private key is the operator key.

```json filename="secrets.json"
{
  "password": "<strong encryption password>",
  "private_key": "0x<64 hex characters>"
}
```

The file must be 16 KiB or smaller. Keep an encrypted offline backup of it.

### Fill in the setup wizard

Enter the values from the table below, and upload the credentials file as **Ciphernode Credentials
JSON**. For contract addresses and deploy blocks, use
[Contract addresses](/operate#contract-addresses).

### Check the logs

Open **Packages → interfold-ciphernode.public.dappnode.eth → Logs**. On the first start, the log
shows `Credential setup completed.` and then `Starting Interfold ciphernode.`

</Steps>

| Wizard field                          | Variable                       | Required | Default in the package                                 |
| ------------------------------------- | ------------------------------ | -------- | ------------------------------------------------------ |
| Network                               | `NETWORK`                      | Yes      | `mainnet` (choices: `mainnet`, `sepolia`, `localhost`) |
| RPC URL                               | `RPC_URL`                      | Yes      | None. Must start with `ws://` or `wss://`.             |
| Chain ID                              | `CHAIN_ID`                     | Yes      | `1`                                                    |
| Node Address                          | `NODE_ADDRESS`                 | Yes      | None. Must match the key in the credentials file.      |
| Interfold Contract Address            | `INTERFOLD_CONTRACT`           | Yes      | The mainnet address                                    |
| Ciphernode Registry Contract          | `CIPHERNODE_REGISTRY_CONTRACT` | Yes      | The mainnet address                                    |
| Bonding Registry Contract             | `BONDING_REGISTRY_CONTRACT`    | Yes      | The mainnet address                                    |
| Slashing Manager Contract             | `SLASHING_MANAGER_CONTRACT`    | Yes      | The mainnet address                                    |
| Fee Token Contract                    | `FEE_TOKEN_CONTRACT`           | Yes      | The mainnet address                                    |
| Deploy blocks (one for each contract) | `*_DEPLOY_BLOCK`               | Yes      | The mainnet values                                     |
| Bootstrap Peers                       | `PEERS`                        | No       | Empty: use the DNS bootstrap of `NETWORK`              |
| Log Level                             | `LOG_LEVEL`                    | No       | `info` (choices: `info`, `debug`, `trace`)             |
| Extra Options                         | `EXTRA_OPTS`                   | No       | Empty. Added to the `interfold start` arguments.       |

Two more variables are set in the package configuration, not in the wizard. `AVAIL_RPC_URL` defaults
to `https://avail-rpc.publicnode.com/` for chain ID 1 and `https://turing-rpc.avail.so/rpc` for
chain ID 11155111. `QUIC_PORT` defaults to `37173`, and the package publishes UDP port 37173.

The package keeps its state in `/data`, on the `ciphernode_data` volume. DAppNode lists this volume
as a backup target. The wallet key and the libp2p key are encrypted there. The password file is also
there, so backups of `/data` must be encrypted and access-controlled.

After it stores the credentials, the package deletes the uploaded file. A restart uses the stored
state and does not need a new upload. An upload with a different password stops startup.

The package health check confirms that the process runs, the files exist, the QUIC listener is
bound, and chain ingestion moves: the node writes a heartbeat file per chain after every successful
read of the chain head, and the check fails when the heartbeat is older than 120 seconds or neither
the head nor the cursor moved for 10 minutes. From 15 minutes after the node started, every enabled
chain must have a heartbeat, so a chain whose RPC endpoint never answers fails the check too. It
does not prove that the node is registered. Read the logs and the
[on-chain status](/operate/registration) to confirm that.

  </Tabs.Tab>
  <Tabs.Tab unmount={false}>

<Steps>

### Install the CLI

Install `interfoldup`, then use it to install a fixed `interfold` release.

```bash
curl -fsSL https://raw.githubusercontent.com/theinterfold/interfold/main/install | bash
interfoldup install --version v0.18.0
interfold --version
```

The last command prints the installed version, for example `interfold 0.18.0`. Add `--system` to
install into `/usr/local/bin` instead of `~/.local/bin`.

### Save the configuration file

Save the file from [Write the configuration file](#write-the-configuration-file) as
`interfold.config.yaml` in the default configuration directory:

- Linux: `~/.config/interfold/`
- macOS: `~/Library/Application Support/interfold/`

The CLI first looks for `interfold.config.yaml` in the current directory and its parent directories,
then in the default directory. Use `--config <path>` to select a file.

### Store the encryption password

```bash
interfold password set
```

The command asks for the password two times. It fails when a password is already set.

### Store the operator key

```bash
interfold wallet set
```

The command asks for the private key without showing it. It prints
`Wallet key has been successfully stored and encrypted.` The node derives its libp2p identity from
the same key.

### Check the configuration

```bash
interfold config check
```

The command must end without a `STALE` line. See
[Check the configuration](#check-the-configuration).

### Start the node

```bash
interfold start -v
```

The log shows `Ciphernode multithread` and `Configured memory-aware compute scheduler`, then the
first sync. The node runs in the foreground until it gets `SIGINT` or `SIGTERM`.

</Steps>

For scripts, `password set --password-stdin` and `wallet set --private-key-stdin` read one line from
standard input. Without these flags, the commands use hidden prompts. They reject secrets in command
arguments.

<Callout type='info'>
  On Sepolia, `interfold ciphernode setup --network sepolia` does the file, password, and key steps
  in one command. It asks for the password, the WebSocket RPC URL, the private key, and the
  configuration directory, unless `--password-stdin`, `--rpc-url`, `--private-key-stdin`, and
  `--config-dir` give them. Without a terminal, it needs all four. It writes the Sepolia addresses
  that the CLI was built with, and a `data_availability` block for Avail Turing. The command
  supports only `sepolia`; for a local chain, start from the project template's
  `interfold.config.yaml`. It refuses to run when a configuration file already exists.
</Callout>

Run the node under a process manager, for example systemd. The node exits with an error when a chain
gateway or the event storage fails, and when startup takes longer than `startup_timeout_secs`. The
process manager restarts it. Give the node more than 60 seconds to stop (see
[Stop and restart](#stop-and-restart)).

  </Tabs.Tab>
  <Tabs.Tab unmount={false}>

The release image `ghcr.io/theinterfold/ciphernode` contains the `interfold` binary at
`/usr/local/bin/interfold`. It runs as the user `ciphernode` (UID 1000) and is built for
`linux/amd64`. The image entrypoint, `ciphernode-entrypoint.sh`, stores the password and the
operator key on the first boot, then starts the node. The node keeps its state on a named volume.
See [Docker state](#docker-state).

<Steps>

### Pull a versioned image

```bash
export CIPHERNODE_IMAGE='ghcr.io/theinterfold/ciphernode:0.18.0'
docker pull "$CIPHERNODE_IMAGE"
```

Image tags use the release version without a `v` prefix.

### Save the configuration file

Save the file from [Write the configuration file](#write-the-configuration-file) as `config.yaml` in
the current directory. The commands below mount it into the container.

### Create a data volume

```bash
docker volume create ciphernode-data
```

The volume holds the key file, the encrypted keys, the event log, and the circuit files.

### Prepare the credentials file

On the first boot, the entrypoint reads the password and the operator key from a JSON file mounted
at `/run/secrets/secrets.json`. It does not read them from environment variables. Create the file
with restrictive permissions. Do not commit it or paste the values into shell history.

```bash
umask 077
install -m 600 /dev/null secrets.json
${EDITOR:-vi} secrets.json
```

```json filename="secrets.json"
{
  "password": "<strong encryption password>",
  "private_key": "0x<64 hex characters>"
}
```

Both values are required. The wallet command derives the libp2p identity from the operator key. Keep
the password and the key in your secret management system.

The entrypoint reads this file only when the volume has no key file or no wallet key. After it uses
the file, it tries to delete it. A read-only mount stays in place, and the boot continues.

Do not set `autopassword` or `autowallet` in `config.yaml` for the image. With `autopassword`, the
node creates a random password before the entrypoint can set the password from this file. With
`autowallet`, the node tries to create a random wallet key before the entrypoint can set the key
from this file.

### Start the container

```bash
docker run -d \
  --name ciphernode \
  --restart unless-stopped \
  --stop-timeout 65 \
  -v ciphernode-data:/home/ciphernode/.local/share/interfold \
  -v "$PWD/config.yaml":/home/ciphernode/.config/interfold/config.yaml:ro \
  -v "$PWD/secrets.json":/run/secrets/secrets.json:ro \
  -p 9091:9091/udp \
  "$CIPHERNODE_IMAGE"
```

### Read the logs

```bash
docker logs -f ciphernode
```

On the first boot, the log shows `Setting password` and `Setting wallet key`. Each boot then shows
`Starting ciphernode`.

</Steps>

The same service in Docker Compose:

```yaml filename="docker-compose.yml"
services:
  ciphernode:
    image: ${CIPHERNODE_IMAGE:?set CIPHERNODE_IMAGE to a versioned release tag}
    restart: unless-stopped
    stop_grace_period: 65s
    volumes:
      - ciphernode-data:/home/ciphernode/.local/share/interfold
      - ./config.yaml:/home/ciphernode/.config/interfold/config.yaml:ro
    secrets:
      - source: ciphernode_credentials
        target: secrets.json
    ports:
      - '9091:9091/udp'

secrets:
  ciphernode_credentials:
    file: ./secrets.json

volumes:
  ciphernode-data:
```

<Callout type='warning'>
  Run this image with its entrypoint. Only the entrypoint sets `E3_CONFIG_DIR` and `E3_DATA_DIR` to
  the volume and stores the password and the key from `secrets.json`. A container that runs with
  `--entrypoint interfold` gets neither, so it keeps its state where the binary stores it by
  default, for example in `/home/ciphernode/.config/interfold/.interfold` on a volume at
  `/home/ciphernode/.config/interfold`. To change such a container to the steps above, remove
  `--entrypoint interfold` (or `entrypoint` in Compose) and keep the same volumes. The entrypoint
  finds the state at `/home/ciphernode/.config/interfold/.interfold` and keeps using it.
</Callout>

The node refuses to start when the container has less than 17 GiB of memory. On Docker Desktop,
increase the memory of the Docker virtual machine. See [Requirements](/operate/requirements).

  </Tabs.Tab>
</Tabs>

## Check the configuration

Contract addresses change when the protocol is deployed again. A node that points at an old address
syncs nothing and reports no error. Before the first start, and after each deployment notice,
compare your configuration with the published deployment manifest:

```bash
interfold config check
```

The command downloads `manifest.json` from the latest GitHub release and compares each chain entry.
Example output for a current Sepolia entry:

```text
Deployment manifest: release v0.19.0-test.1
sepolia: up to date
```

Example output for a stale entry:

```text
sepolia:
  STALE interfold: config has 0x38A8A686…, published is 0xc5DD9418…
  warn  ciphernode_registry: deploy_block 11508403, published is 11855915
```

| Line    | Meaning                                                            | Fails the check |
| ------- | ------------------------------------------------------------------ | --------------- |
| `STALE` | A contract address or the `chain_id` does not match the manifest.  | Yes             |
| `warn`  | A `deploy_block` does not match the manifest.                      | No              |
| `note`  | A published contract is not configured, or the network uses mocks. | No              |

The command exits with a non-zero status when a line is `STALE`. You can use it as a gate before a
restart in a process manager or a CI job. Use `--chain <name>` to check one chain. Use
`--manifest-url <url>` to check against a specific manifest file.

## Watch the node

The `-v` flag sets the log level. The flags are global, so they work with every command.

| Flag   | Level | Output                   |
| ------ | ----- | ------------------------ |
| (none) | WARN  | Warnings and errors only |
| `-v`   | INFO  | Normal operation         |
| `-vv`  | DEBUG | Detailed debug output    |
| `-vvv` | TRACE | Full trace               |
| `-q`   | ERROR | Errors only              |

Logs at `-vv` and higher can contain the endpoint URL. If the URL contains an API key, remove it
before you share logs.

These events show the progress of an E3 in the node log:

| Event                       | Meaning                                                   |
| --------------------------- | --------------------------------------------------------- |
| `E3Requested`               | The node saw a new E3 request.                            |
| `TicketGenerated`           | The node calculated its best sortition ticket for the E3. |
| `CiphernodeSelected`        | The node is a member of the committee.                    |
| `KeyshareCreated`           | The node made its key share.                              |
| `PublicKeyAggregated`       | The committee public key is ready to publish.             |
| `CommitteePublished`        | The committee public key is on-chain.                     |
| `CiphertextOutputPublished` | The encrypted output is on-chain. Decryption starts.      |
| `DecryptionshareCreated`    | The node made its decryption share.                       |
| `PlaintextAggregated`       | The decrypted result is ready to publish.                 |
| `PlaintextOutputPublished`  | The result is on-chain.                                   |
| `E3RequestComplete`         | The node started its cleanup for the E3.                  |

When the node runs, some commands run inside the node through the local control port:
`ciphernode status`, `wallet get`, `net get-peer-id`, `config get`, `rev`,
`print-env --chain <name>`, `noir status`, and `events query`. See
[Commands that run inside a running node](/reference/cli#commands-that-run-inside-a-running-node).
For a visual view, turn on the [node dashboard](/operate/dashboard).

## Stop and restart

On `SIGINT` or `SIGTERM`, the node stops its actors and writes its event log and store to disk. This
shutdown has a limit of 60 seconds. Set the stop timeout of your process manager above 60 seconds.
The DAppNode package and the examples on this page use 65 seconds.

The node locks its data directory (`interfold.lock`) while it runs. A second node process with the
same data directory does not start.

After a crash, a restore, or a binary upgrade, check the stored state before you start the node. Do
these steps with the node stopped:

<Steps>

### Validate the state

```bash
interfold node validate
```

The command changes no files. It ends with `VALIDATION PASSED` or reports `FAIL` lines, and it exits
with a non-zero status on a failure. In Docker, run it through the image entrypoint with the same
volume and configuration:

```bash
docker run --rm \
  -v ciphernode-data:/home/ciphernode/.local/share/interfold \
  -v "$PWD/config.yaml":/home/ciphernode/.config/interfold/config.yaml:ro \
  "$CIPHERNODE_IMAGE" \
  node validate --config /home/ciphernode/.config/interfold/config.yaml
```

### Repair a recoverable tail

If the report shows only an uncommitted event-log tail, or a stale sortition projection, run:

```bash
interfold node validate --repair
```

The repair indexes complete uncommitted frames again, cuts a torn tail, or rebuilds the sortition
projection from intact events. It never removes an indexed event.

Validation checks the storage schema before it reads or repairs event logs. An unsupported schema
reports the recovery instruction and skips all event and snapshot checks.

### Start the node

Start the node only when the validation passes.

</Steps>

<Callout type='warning'>
  Do not start a node when validation reports `FAIL` and the repair cannot fix it. Copy the data
  directory before you try a restore or a new sync. The repair cannot fix corruption in committed
  records or a storage schema that the binary does not support.
</Callout>

When the node cannot write or flush its event log, it stops so that the process manager can restart
it. Repeated storage failures are an infrastructure problem. Stop the node, keep a copy of the data,
and run the validation before the next start. When a release changes the storage schema, see
[Upgrades](/operate/upgrades).

## Data and backups

A CLI node keeps all state in a `.interfold` directory next to its configuration file. The password
file is in `.interfold/config/<name>/`. The key store and the event log are in
`.interfold/data/<name>/`. Run `interfold config get db_file` to print the path on your host. The
[requirements](/operate/requirements#disk-and-storage) page lists the contents. The Docker image
keeps the state on its volume. See [Docker state](#docker-state).

Back up the complete `.interfold` directory as one unit, while the node is stopped. The event log
refers to files in its `event-blobs-v1` directory. Do not delete those files to free space.

<Callout type='warning'>
  The key store holds the encrypted operator key, and the password file is next to it. A copy of the
  directory can sign as your operator. Encrypt backups and control access to them. Do not run two
  nodes from copies of the same directory. See [Migrate a Node](/operate/migrating).
</Callout>

## Docker state

### Where the node stores its state

The image entrypoint sets `E3_CONFIG_DIR=/home/ciphernode/.local/share/interfold/config` and
`E3_DATA_DIR=/home/ciphernode/.local/share/interfold/data`, unless the container sets them. Thus the
node keeps all of its state on the volume at `/home/ciphernode/.local/share/interfold`:

| Path on the volume    | Contents                                                                        |
| --------------------- | ------------------------------------------------------------------------------- |
| `config/_default/key` | Key file with the password that encrypts the stored keys                        |
| `data/_default/db`    | Key/value store: wallet key, libp2p keypair, key shares, and protocol snapshots |
| `data/_default/log.*` | Event logs                                                                      |

A restart, a new container, and a new image all keep this state. `docker rm` does not delete a named
volume.

These variables override `config.yaml`, so the entrypoint never uses them to move state that exists.
If `config.yaml` sets `config_dir`, `data_dir`, `key_file`, or `db_file`, the node uses that
location. If a key file or database exists at `/home/ciphernode/.config/interfold/.interfold`, for
example on a volume that is mounted at `/home/ciphernode/.config/interfold`, the node keeps using
it. If state exists both there and on the volume, the container does not start. Keep only the state
that the node last used, and start the container again. You can also set your own `E3_CONFIG_DIR`
and `E3_DATA_DIR` for the container.

In these cases the node does not use the entrypoint's variables, so run other `interfold` commands
through the entrypoint, which chooses the same location. For example, run
`docker exec ciphernode ciphernode-entrypoint.sh wallet get --config /home/ciphernode/.config/interfold/config.yaml`.
The command in [Validate the state](#validate-the-state) also runs through the entrypoint.

### Move state from an earlier image

Earlier images did not set these variables. A node that started from such an image, without a volume
at `/home/ciphernode/.config/interfold`, keeps its state inside the container, in
`/home/ciphernode/.config/interfold/.interfold`. That directory is not on the volume. When you
remove or recreate that container, you lose the key file, the key/value store, and the event log.
The key/value store holds the key shares of the node, and the chain cannot restore them.

<Callout type='warning'>
  Do not remove or recreate the old container before you copy its state. `docker rm`, `docker
  compose down`, and `docker compose up` with a new image all remove the old container. The copy
  puts the key file and the stored keys on the volume. Run `interfold node reset-data` only after
  the copy, and only with the new image. Never use `interfold nodes purge` for this migration.
</Callout>

Do this procedure one time for each node, when the node serves no active E3. An earlier image uses
storage schema 7 or earlier, and v0.19.0 uses schema 8. The procedure therefore resets the state
after the copy. The reset keeps the operator key and the libp2p keypair. See
[Reset node state](/operate/upgrades#reset-node-state).

The commands use the container name `ciphernode` and the volume name `ciphernode-data`. For Docker
Compose, use the names that `docker ps -a` and `docker volume ls` show. Each one-off container runs
the new image through its entrypoint, with the same volume and configuration file:

```bash
new_image() {
  docker run --rm \
    -v ciphernode-data:/home/ciphernode/.local/share/interfold \
    -v "$PWD/config.yaml":/home/ciphernode/.config/interfold/config.yaml:ro \
    "$CIPHERNODE_IMAGE" \
    "$@" --config /home/ciphernode/.config/interfold/config.yaml
}
```

1. Set the image of the new release, and pull it. The helper and the later steps use this variable.

   ```bash
   export CIPHERNODE_IMAGE='ghcr.io/theinterfold/ciphernode:0.19.0'
   docker pull "$CIPHERNODE_IMAGE"
   ```

2. Find out how the old container starts, and whether a stop removes it:

   ```bash
   docker inspect -f '{{json .Config.Entrypoint}} {{.HostConfig.AutoRemove}}' ciphernode
   ```

   Continue only if the output is `["interfold"] false`, or one path that ends with `/interfold`
   followed by `false`. For all other output, do not stop the container, and contact the protocol
   team:
   - `["ciphernode-entrypoint.sh"]` is the entrypoint of the earlier image. At each start, it sets
     the password again, and `interfold password set` refuses a key file that exists. Such a
     container cannot start again after a stop.
   - `true` means that the container started with `--rm`. A stop removes the container and the state
     inside it.

3. Make sure that no E3 is active on the network. The output must be `0`. Get the Interfold address
   from [Contracts and addresses](/reference/contracts).

   ```bash
   cast call <Interfold> "activeE3Count()(uint256)" --rpc-url <RPC_URL>
   ```

4. Record the operator address and the peer ID from the old container, while it runs. If a command
   fails or prints no value, stop and contact the protocol team.

   ```bash
   docker exec ciphernode interfold wallet get --config /home/ciphernode/.config/interfold/config.yaml
   docker exec ciphernode interfold net get-peer-id --config /home/ciphernode/.config/interfold/config.yaml
   ```

5. Make sure that the volume has no `data` or `config` directory. If the output shows either name,
   stop and contact the protocol team.

   ```bash
   docker run --rm \
     -v ciphernode-data:/home/ciphernode/.local/share/interfold \
     --entrypoint ls \
     "$CIPHERNODE_IMAGE" \
     -A /home/ciphernode/.local/share/interfold
   ```

6. Stop the old container. Do not remove it.

   ```bash
   docker stop --time 65 ciphernode
   ```

7. Copy the `data` and `config` directories from the old container to the volume. `docker cp` sends
   each directory as a tar stream, so the key file does not go to the host disk.

   ```bash
   for dir in data config; do
     docker cp "ciphernode:/home/ciphernode/.config/interfold/.interfold/$dir" - |
       docker run --rm -i \
         -v ciphernode-data:/home/ciphernode/.local/share/interfold \
         --entrypoint tar \
         "$CIPHERNODE_IMAGE" \
         -xf - -C /home/ciphernode/.local/share/interfold
   done
   ```

8. Make sure that the copy is complete. The output must show `key`, `db`, and `log.0`. If a name is
   missing, stop and contact the protocol team.

   ```bash
   docker run --rm \
     -v ciphernode-data:/home/ciphernode/.local/share/interfold \
     --entrypoint ls \
     "$CIPHERNODE_IMAGE" \
     /home/ciphernode/.local/share/interfold/config/_default \
     /home/ciphernode/.local/share/interfold/data/_default
   ```

9. Reset the state:

   ```bash
   new_image node reset-data --yes
   ```

   The output must end with this line. If it says `No identity was present`, stop and contact the
   protocol team.

   ```text
   The operator key and libp2p identity were preserved. Verify with: interfold wallet get --name _default
   ```

   If the command refuses, use the cases in
   [If the command refuses](/operate/upgrades#if-the-command-refuses). Add `--allow-active-e3s` only
   in the last case. In each other case, start the old container again:

   ```bash
   started=$(date -u +%Y-%m-%dT%H:%M:%SZ)
   docker start ciphernode
   ```

   Use `docker start` also for Docker Compose. `docker compose up` removes the old container, which
   holds the state that the node uses. If the container does not start, stop and contact the
   protocol team, and keep the copy on the volume.

   The log from before the stop also holds the release lines, so read only the log since the start.
   When it shows `Ciphernode release is accepted` or `Acknowledging ciphernode release`, remove the
   copy from the volume. Then do what the case tells you.

   ```bash
   docker logs --since "$started" ciphernode
   ```

   ```bash
   docker run --rm \
     -v ciphernode-data:/home/ciphernode/.local/share/interfold \
     --entrypoint rm \
     "$CIPHERNODE_IMAGE" \
     -rf /home/ciphernode/.local/share/interfold/data /home/ciphernode/.local/share/interfold/config
   ```

10. Run these commands. The address and the peer ID must be equal to the values from step 4. If they
    differ, or a command fails, stop and contact the protocol team.

    ```bash
    new_image wallet get
    new_image net get-peer-id
    ```

11. Validate the state. Continue only if the report shows `empty store will be initialized` and ends
    with `VALIDATION PASSED — state is intact and consistent.` Otherwise, do not start the new
    image. Keep the old container and the volume, and contact the protocol team.

    ```bash
    new_image node validate
    ```

12. Start the new image. For `docker run`, rename the old container first, then use the command in
    [Start the container](#start-the-container):

    ```bash
    docker rename ciphernode ciphernode-old
    ```

    For Docker Compose, make sure that `CIPHERNODE_IMAGE` names the new image. Remove the
    `entrypoint:` line from the service: step 2 required the old container to start `interfold`
    directly, but the new image must start through its own entrypoint, which uses the volume. Then
    run `docker compose up -d`. This command replaces the old container.

13. Make sure that the log shows `Ciphernode release is accepted`, and that this command shows the
    operator address from step 4:

    ```bash
    docker exec ciphernode ciphernode-entrypoint.sh wallet get --config /home/ciphernode/.config/interfold/config.yaml
    ```

14. For `docker run`, remove the old container only after step 13 succeeds.

## Networking

Open the QUIC UDP port (default `9091`) for inbound traffic. Do not open the control port `50505`.
[Requirements](/operate/requirements#network-ports) lists all ports.

When `peers` is empty, the node dials the DNS bootstrap address of its network profile. Mainnet uses
`/dnsaddr/bootstrap.interfold.network`. Sepolia uses `/dnsaddr/bootstrap-sepolia.interfold.network`.
The profile also sets a network ID that every Interfold libp2p protocol uses. A mainnet node and a
Sepolia node therefore cannot join the same network, also when a peer address is wrong.

To dial specific peers, list them in the configuration:

```yaml
node:
  network: mainnet
  peers:
    - '/dns4/node1.example.com/udp/9091/quic-v1'
    - '/ip4/192.0.2.10/udp/9091/quic-v1'
```

You can also add a peer at start with `interfold start --peer <multiaddr>`. A mainnet profile
refuses the Sepolia bootstrap address. A Sepolia profile replaces the mainnet bootstrap address with
the Sepolia one.

### Run a bootstrap node

A bootstrap node is a peer that other nodes dial first to find each other. Start it with
`interfold start --bootstrap`. The node reads the events of the Interfold contract and joins the
network like a full node, but it does not serve on committees, generate proofs, sign votes, or send
transactions. It therefore does not need the memory of the prover, and its address needs no ETH.
When it starts, it fetches the history of open E3s from its peers like a full node. If no peer can
serve that history, it starts without it, so it can start when no other node is running. Its request
router expects no protocol recipients and keeps no deferred protocol backlog.

It needs the same setup as a full node: a configuration with the network profile and the chains, a
password, and a wallet key. The wallet key sets the node address and the libp2p peer ID, so use a
key that no other node uses. The key does not have to belong to a registered operator. Open its QUIC
UDP port, and add its address to the `peers` of the other nodes, for example
`/dns4/bootstrap.example.com/udp/9091/quic-v1`.

Give a bootstrap node a data directory of its own. On its first start, a node records its role (full
or bootstrap) in its data directory. A node does not start on a data directory that a node of the
other role used. Releases without bootstrap mode do not check the role, so do not start an older
release on the data directory of a bootstrap node. To change the role of a node, stop the node and
run `interfold node reset-data`, which keeps the wallet key.

### Deferred protocol events

A full node can receive an E3 event before the actor that consumes it starts. The request router
keeps these events in order for recipients declared by the installed extensions. Each E3 has a limit
of 4,096 deferred entries and 1 GiB of accounted bytes. The router has a shared limit of 16,384
entries and 3 GiB. Each recipient copy counts toward both limits, including shared payload bytes.

Each entry reserves its encoded bytes, nested inline storage, and 64 bytes per allocation candidate.
The reservations cover strings, byte buffers, collections, their elements, and shared payload
fields. Large contiguous buffers add constant allocation overhead. They have no extra charge per
payload byte. Shared bytes retain no spare capacity, and deferred copies compact collections inside
shared keys and threshold shares. Each entry also reserves twice its inline event size for queue
capacity.

These limits cover four concurrent E3s with the largest supported committee (N=19, H=14) and the
secure 8192-degree preset. The slashing recipients start at committee finalization. Keyshare and
public-key recipients start at local selection. Only the plaintext recipient retains the complete
local DKG history until ciphertext output arrives.

The late-recipient allowance is 1,536 records and 640 MiB per E3. It includes the C1–C3 witnesses,
the complete request payloads retained by computation failures, C4 inputs, peer shares, and document
envelopes. Four such histories use 2.5 GiB, leaving 512 MiB of margin below the shared byte limit.

The 3 GiB ceiling includes allocation reservations, but it does not measure exact resident memory.
In an 8 GiB memory budget, allow another 1.5 GiB for fragmentation, freed storage, and an in-flight
event. The remaining 3.5 GiB covers other actors, the process baseline, and the system. The router
memory regression checks this allowance with contiguous and separately allocated small payloads.
These are buffer allowances, not total node memory requirements or limits on incoming-event
decoding. Proof workers need a separate allowance. See [Requirements](/operate/requirements) for
node sizing.

If a limit is exceeded, the router logs `Deferred delivery failed` at ERROR and clears the affected
recipient's deferred queue. It retains the failure record until E3 teardown or restart and stops
adding events to that queue. Other E3s and live delivery continue. The affected E3 can fail at its
existing deadline. Deferred queues remain in memory only, so a restart does not restore their
pre-checkpoint events.

## Command reference

The commands on this page are `start`, `config check`, `password set`, `wallet set`,
`node validate`, and `ciphernode setup`. Global flags work with every command: `--config <path>`,
`--name <profile>`, `-v`, and `-q`. The [CLI Reference](/reference/cli) lists every command and
flag. For a schema change that needs `interfold node reset-data`, see [Upgrades](/operate/upgrades).
