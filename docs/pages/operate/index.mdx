# Ciphernode Operators

This page is the starting point for operators who want to run a ciphernode on the Interfold. It
explains what a ciphernode does, which contracts control an operator position, and the order of the
setup steps. At the end, you know which page to open for each step and which contract addresses to
use.

<Callout type='info'>
  The Interfold dashboard has a guided operator setup at [Run a
  ciphernode](https://dashboard.theinterfold.com/#operator). It reads the live `BondingRegistry` and
  sends each on-chain step from your browser wallet: connect a wallet, authorize the bond owner,
  bond FOLD, register the ciphernode, and buy tickets. You must still run the node software
  yourself.
</Callout>

## What a ciphernode does

A ciphernode is a node that holds one share of a committee secret key. The protocol selects a
committee of ciphernodes for each E3. No single ciphernode can decrypt the output. Decryption needs
T + 1 decryption shares. For each committee that selects it, a ciphernode does this work:

- It submits sortition tickets for the E3 (`submitTicket` on `CiphernodeRegistry`).
- It takes part in distributed key generation (DKG) and keeps its key share.
- It helps the committee publish one public key for the E3.
- It makes a decryption share of the E3 output after the compute provider publishes the ciphertext.
- It generates zero-knowledge proofs for its DKG and decryption work.

The node also acknowledges its software release on-chain when it starts (`acknowledgeNodeRelease` on
`NodeReleaseRegistry`). An operator is active only when its acknowledged release meets the required
protocol version and node generation. See [Upgrades](/operate/upgrades) for the release rules.

A committee member that fails its duties, or breaks a protocol rule, can lose part of its bond and
tickets. `SlashingManager` handles these penalties. See
[Exits, Rewards & Slashing](/operate/exits-and-slashing).

## Contracts for operators

Each operator position uses two keys. The operator key is the hot key that the node loads. The bond
owner is the wallet or Safe that funds the position and receives exit payouts and rewards. The
contracts below store the position and its state.

| Contract (source file)                                     | What it does for an operator                                                                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `BondingRegistry` (`registry/BondingRegistry.sol`)         | Stores the bond owner, the FOLD bond, and the ticket balance. It registers operators, decides active status, and queues exits. |
| `CiphernodeRegistry` (`CiphernodeRegistryOwnable.sol`)     | Keeps the set of registered ciphernodes. It accepts sortition tickets and finalizes each committee.                            |
| `Interfold` (`Interfold.sol`)                              | Records each E3 and its stage. Requesters call it to request an E3.                                                            |
| `SlashingManager` (`slashing/SlashingManager.sol`)         | Processes slash proposals, appeals, and bans.                                                                                  |
| `NodeReleaseRegistry` (`registry/NodeReleaseRegistry.sol`) | Stores the required node release and the release that each operator acknowledged.                                              |
| `E3RefundManager`                                          | Calculates and pays refunds when an E3 fails.                                                                                  |
| `InterfoldToken` (FOLD)                                    | The bond token. The bond owner bonds FOLD for each operator.                                                                   |
| `InterfoldTicketToken` (tFOLD)                             | A non-transferable token that wraps the ticket collateral. The registry mints it to the operator key.                          |

On both networks, operators bond FOLD (`InterfoldToken`). The ticket collateral is an ERC-20 token
that `InterfoldTicketToken` wraps. Mainnet uses sUSDS shares, and Sepolia uses `MockUSDC`. The fee
token is separate: requesters pay E3 fees with it. Mainnet uses USDS as the fee token, and Sepolia
uses `MockUSDC`.

## Operator lifecycle

An operator position moves through the stages below. The stepper plays automatically. Select a stage
to read it. The table after the stepper lists the same states.

<Lifecycle label="Operator lifecycle">
  <Stage title="Set up" actor="Operator" event="OperatorNodeReleaseAcknowledged">

Install the node software, write its configuration, and store the operator key. When the node
starts, it syncs the contract history and acknowledges its release on-chain.

  </Stage>
  <Stage title="Register and bond" actor="Operator key, bond owner" event="CiphernodeAdded">

The operator key calls `setBondOwner`. The bond owner bonds FOLD with `bondCiphernodeFor`, then
calls `registerOperatorFor`. Registration needs the full `requiredCiphernodeBond`.

  </Stage>
  <Stage title="Tickets" actor="Bond owner" event="TicketBalanceUpdated">

The bond owner deposits ticket collateral with `addTicketBalanceFor`. The registry mints tFOLD to
the operator key. Available tickets are `floor(ticket balance / ticketPrice)`.

  </Stage>
  <Stage title="Active" actor="BondingRegistry" event="OperatorActivationChanged">

The operator becomes active when it is registered, not banned, bonded above the active floor, holds
at least `minTicketBalance` tickets, and runs an accepted release.

  </Stage>
  <Stage title="Selected for a committee" actor="Ciphernode" event="SortitionCommitteeFinalized">

For each E3 request, the node scores its tickets and submits its best ticket once. The lowest scores
form the committee, with at most one operator for each bond owner. The committee runs DKG and later
decrypts the output.

  </Stage>
  <Stage title="Exit" actor="Bond owner" event="CiphernodeDeregistrationRequested">

The bond owner or the operator key calls `deregisterOperatorFor`. All collateral enters the exit
queue. After `exitDelay`, `claimExitsFor` pays the collateral to the bond owner.

  </Stage>
</Lifecycle>

| State            | Condition                                                                                                      | Next action                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Not configured   | `bondOwnerOf(operator)` returns the zero address. Calls that need the bond owner revert with `NotBondOwner`.   | The operator key calls `setBondOwner`.                               |
| Bonded           | The bond owner bonded FOLD, but the operator is not registered.                                                | The bond owner calls `registerOperatorFor`.                          |
| Registered       | The operator is in the registry, but one activation condition is not met (often, no tickets yet).              | The bond owner calls `addTicketBalanceFor`.                          |
| Active           | All activation conditions are met. `isActive(operator)` returns `true`.                                        | The node takes part in sortition for new E3s.                        |
| Inactive         | Registered, but the bond, the tickets, the release, or a ban no longer meets the rules.                        | Add collateral, upgrade the node, or refresh status.                 |
| Exit in progress | `deregisterOperatorFor` queued all collateral. `hasExitInProgress(operator)` is `true` until `exitDelay` ends. | After the delay, claim the exit. To return, bond and register again. |

[Registration & Bonding](/operate/registration) gives the commands, the activation rules, and the
economic parameters. [Tickets & Sortition](/operate/tickets-and-sortition) explains committee
selection.

## Requirements summary

| Requirement       | Summary                                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| FOLD bond         | `requiredCiphernodeBond` for each operator. The mainnet deployment value is 32,000 FOLD.                          |
| Ticket collateral | At least `minTicketBalance` tickets. On mainnet, one ticket is 1,000 sUSDS shares and the minimum is one ticket.  |
| ETH               | Gas for the bond owner transactions, and for the operator key (ticket submissions and release acknowledgment).    |
| Memory            | On Linux, the node does not start below 17 GiB (4 GiB reserve plus one 13 GiB prover job). The guidance is 32 GB. |
| Network           | One open inbound UDP port for QUIC. The default is `9091`.                                                        |
| RPC endpoints     | A WebSocket Ethereum endpoint with log history from the contract deploy blocks, and an Avail HTTP endpoint.       |

The full list is on [Ciphernode Requirements](/operate/requirements). Read the live economic values
on-chain before you deposit (see
[Registration & Bonding](/operate/registration#economic-parameters)).

## Set up a ciphernode

Do the setup pages in this order:

1. Check the hardware, network, and endpoint needs on [Requirements](/operate/requirements).
2. Install and start the node on [Run a Ciphernode](/operate/running).
3. Test your Ethereum endpoint on [RPC Endpoints](/operate/rpc-endpoints) before the first sync.
4. Authorize the bond owner, bond, register, and buy tickets on
   [Registration & Bonding](/operate/registration).

For help with setup, join the [Interfold technical chat](https://t.me/interfoldhq_technical).
