# Verifying the compute provider

An OpenVM proof identifies an executable and a VM configuration. It does not identify the source
checkout that produced them. Verification therefore needs both build evidence and deployment checks.

## Build evidence

1. Select a clean source commit and its checked-in lockfiles.
2. Follow the OpenVM build instructions in `crates/support/openvm/README.md`.
3. Generate the application key and executable.
4. Run the worker's `prepare` command to derive the aggregation key and application commitments.
5. Compare an independent rebuild with the expected commitments.
6. Record the proving artifacts, verifier artifact, and toolchain versions.

The native host and guest must use the same processor and input policy. The guest derives the
ciphertext, SAFE commitment, parameter hash, and input root. It must not accept those values as
unverified output claims.

Run `interfold-openvm-prover check <config.json>` before service startup. This command checks the
executable identity, VM identity, aggregation-key compatibility, and verifier artifact checksum. It
does not certify that the source is audited or that the build is reproducible.

## Deployment checks

The receipt identity is:

`keccak256(abi.encode(keccak256("INTERFOLD_OPENVM_RECEIPT_V1"), halo2Verifier, appExeCommit, appVmCommit))`

Check all three contracts:

- The generated Halo2 verifier must have the runtime code produced by the checked artifact.
- `OpenVmReceiptVerifier` must contain the prepared executable and VM commitments.
- `OpenVmBfvCiphertextVerifier` must reference that receipt verifier and its identity.

CRISP's `openVmVerifier()` and `imageId()` must also match. The protocol wrapper's immutable
identity does not make application-owner changes harmless: inconsistent application settings can
prevent an active round from completing.

Interfold snapshots the protocol verifier when it accepts an E3 request. Drain active rounds before
a live verifier migration. A proxy upgrade remains a separate governance risk.

## Provenance manifest

From the clean source checkout, run:

```sh
pnpm provenance:manifest --config <worker-config.json> --prover <worker-binary> \
  --rpc <rpc-url> --verifier <OpenVmBfvCiphertextVerifier-address> --out <new-manifest.json>
```

The command records source and artifact digests, application commitments, worker validation, and the
deployed verifier bindings. It compares the deployed Halo2 runtime with a read-only simulation of
the checked artifact's creation bytecode. It does not submit a transaction.

Missing or failed checks produce `complete: false` and an `unresolved` list. A complete record is
not evidence of an independent source rebuild. The manifest states
`sourceReproductionChecked: false`; retain that separate build evidence with the release.

File SHA-256 digests are integrity checks. They are not application commitments or receipt
identities. Do not substitute one for another.

## Journal and proof checks

The guest reveals SHA-256 of nine consecutive ABI words:

1. Chain ID
2. Interfold address
3. Full uint256 E3 ID
4. Encryption scheme ID
5. Committee public-key commitment
6. Ciphertext hash
7. SAFE ciphertext commitment
8. Parameter hash
9. Input root

The protocol reconstructs the domain and output fields. The application independently compares the
parameter hash and input root with its stored values. Both verification calls must pass.

Use `pnpm openvm proof-test` to verify a supplied real receipt and reject changed proof data,
journal fields, and application commitments. Use `pnpm openvm service-e2e` to test the HTTP
dispatch, callback, and automatic ciphertext publication on an isolated local chain.

A test must state which dependencies are mocked. A real compute proof alone does not demonstrate
distributed key generation, ballot proofs, external data availability, or threshold-decryption
proofs.

The compute implementation and OpenVM verifier integration remain unaudited.
