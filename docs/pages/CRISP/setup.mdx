# Getting Started with CRISP

This guide will walk you through the steps to set up and run CRISP locally. CRISP is a full
reference implementation of an E3 Program, built with a modern architecture that includes smart
contracts, zero-knowledge circuits, frontend applications, and secure computation components.

## Prerequisites

Before getting started, ensure you have installed:

- [Rust](https://rust-lang.org/tools/install/)
- [Foundry](https://getfoundry.sh)
- [Node.js](https://nodejs.org/en/download)
- [pnpm](https://pnpm.io)
- [MetaMask](https://metamask.io)
- Noir toolchain ([`nargo`](https://noir-lang.org/docs/installation),
  [`bb`](https://barretenberg.aztec.network/docs/getting_started))

## Quick Start

First configure the OpenVM worker and verifier as described below. Then, from `examples/CRISP`:

```bash
# Install dependencies and build everything
pnpm dev:setup

# Start all services (Anvil, contracts, ciphernodes, program server, coordination server, and UI)
pnpm dev:up
```

`dev:up` runs `scripts/dev.sh`, which:

1. Starts Anvil with chain ID 31337
2. Deploys all contracts (Interfold, CRISPProgram, verifiers, registries) via
   `scripts/crisp_deploy.sh`
3. Watches the configured local randomness provider and fulfills each request in a later block. This
   supports both the direct mock and the Chainlink adapter with the local coordinator mock.
4. Starts Ciphernodes using `interfold.config.yaml` via `scripts/dev_cipher.sh`
5. Launches the program server via `scripts/dev_program.sh`
6. Starts the coordination server (Rust) via `scripts/dev_server.sh` on port `4000`
7. Starts the React client via `scripts/dev_client.sh` on port `3000`

All services run concurrently and will automatically restart if needed.

### Additional Commands

```bash
# Recompile Noir circuits and generate verifiers
pnpm compile:circuits

# Open the interactive CLI to start voting rounds
pnpm cli

# Run end-to-end tests
pnpm test:e2e
```

### Deployed Contract Addresses

The contract addresses are automatically configured in `interfold.config.yaml` and the server `.env`
file. After running `pnpm dev:up`, the deployment logs will show the deployed contract addresses,
which are also saved in `packages/crisp-contracts/deployed_contracts.json`.

### Using the Application

Once everything is running, you can:

1. Navigate `http://localhost:3000` for the client interface
2. Add the public development key to your test wallet:
   `0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80`
3. Press `Connect Wallet` button and complete the association with your MetaMask account
4. Switch to the local network with chain ID 31337 (this will be handled automatically by the app.
   You just need to press on the connected account on the frontend and select the network. Then,
   complete the configuration on MetaMask pop-up).
5. Open a new terminal, run `pnpm cli` and start a new E3 Round.
6. Refresh and interact with the round following the Client interface.

## Configuration

### Ciphernode Configuration

The `interfold.config.yaml` file configures the ciphernode network and the program service. The
program service requires real OpenVM proofs by default:

```yaml
program:
  dev: false
  openvm:
    repository: /absolute/path/to/interfold
    prover_bin: /absolute/path/to/interfold-openvm-prover
    prover_config: /absolute/path/to/deployment/prover.json
```

### OpenVM Configuration

Build the pinned guest and prover, then generate the application identity and aggregation key. The
repository's `crates/support/openvm/README.md` describes the artifact and CUDA requirements.
`interfold program compile` builds the native support service; it does not generate guest keys.

Before contract deployment, export `OPENVM_APP_EXE_COMMIT` and `OPENVM_APP_VM_COMMIT` from the
prepared identity. Select one verifier source:

- `OPENVM_VERIFIER_ARTIFACT` and `OPENVM_VERIFIER_SHA256`: deploy the checksummed bytecode artifact.
- `OPENVM_HALO2_VERIFIER` and `OPENVM_HALO2_RUNTIME_CODE_HASH`: check an existing verifier's code.

The deployment installs `OpenVmReceiptVerifier` and the protocol's `OpenVmBfvCiphertextVerifier`.
Missing or inconsistent settings stop deployment. Other local test mocks do not disable compute
verification.

Changing the guest requires new matching artifacts and verifier bindings. Keep keys and
machine-specific paths outside version control. Existing rounds retain their request-time verifier;
drain them before a live migration. The historical activation scripts do not migrate to OpenVM.

The service accepts HTTP compute jobs and callback URLs without authentication. Keep it on an
isolated network or behind authenticated admission control. Its queue is in memory; operators must
reconcile interrupted jobs and failed callbacks. See [Compute Provider](/compute-provider).

### Environment Variables

The `pnpm dev:setup` command automatically creates `.env` files for the server and client from the
`.env.example` templates. The server's `.env` file is automatically populated with contract
addresses after deployment.

## Running Individual Components

While `pnpm dev:up` runs everything together, you can also run components separately:

```bash
# Start only the local EVM node
anvil --host 127.0.0.1 --chain-id 31337 --block-time 1

# Start only the ciphernodes (requires Anvil running)
./scripts/dev_cipher.sh

# Start only the program server (requires ciphernodes)
./scripts/dev_program.sh

# Start only the coordination server (requires program server)
./scripts/dev_server.sh

# Start only the client (requires coordination server)
./scripts/dev_client.sh

# Run the CLI (requires all services)
pnpm cli
```
