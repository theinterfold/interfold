# RPC Endpoint Requirements

A ciphernode reads its whole history from an Ethereum RPC endpoint before it can take part in a
committee. Most node problems reported during setup are endpoint problems, so it is worth
checking an endpoint before the first run.

## What the node asks for

| Requirement          | Value                       | Why                                                        |
| -------------------- | --------------------------- | ---------------------------------------------------------- |
| **Archive history**  | Required                    | The first sync reads from the contract deploy block         |
| **`eth_getLogs`**    | 10,000 block range, or less | The node narrows its range by itself when a provider refuses |
| **Rate limit**       | ~25 requests/second         | The whole first sync is a few hundred calls                 |
| **WebSocket**        | `wss://` recommended        | Live events arrive by subscription after the sync           |

The node starts at a 10,000 block range and halves it when a provider rejects the range, so an
endpoint with a smaller cap still works. It costs more calls: a 5,000,000 block history takes
500 calls at 10,000 blocks and 500,000 calls at 10 blocks.

## Archive history is the one that cannot be worked around

An endpoint that has discarded old state answers a historical `eth_getLogs` with an **empty
result and no error**. A node cannot tell that apart from "no events happened here", so it
finishes its first sync, reports success, and is missing the events that registered it. It then
stays inactive with nothing in the log to explain why.

Measure first, and do not rely on a provider's marketing copy. Free tiers of several well known
providers are not archive.

## Test an endpoint in one command

Run this before you point a node at a new endpoint. Replace the URL, and use your network's
registry address and deploy block.

```bash
RPC=https://your-endpoint.example
REGISTRY=0x118B7DFE26007ca2f618593A045EE474dF9DFBDf   # Sepolia
DEPLOY=0xB22DB5                                        # 11677109
UNTIL=0xB254D4                                         # 11687124, ~10k blocks later

# 1. Archive check: this must return contract code, not an error.
curl -s -X POST $RPC -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"eth_getCode\",\"params\":[\"$REGISTRY\",\"$DEPLOY\"]}"

# 2. Range check: this must return logs, not an error and not an empty list.
curl -s -X POST $RPC -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"eth_getLogs\",\"params\":[{\"fromBlock\":\"$DEPLOY\",\"toBlock\":\"$UNTIL\",\"address\":\"$REGISTRY\"}]}"
```

Read the results this way:

- `eth_getCode` returns a long `0x60806040...` string: the endpoint keeps the history.
- `eth_getCode` returns an error such as `state at block #... is pruned`, or returns `0x`: the
  endpoint is **not** usable, whatever its `eth_getLogs` does.
- `eth_getLogs` returns an error naming a block range: the range cap is below 10,000. The node
  handles this, and the sync takes more calls.
- `eth_getLogs` returns `[]` on a range where the archive check passed: treat the endpoint as
  unusable and report it.

## Measured endpoints

Measured against Sepolia on 15 September 2026, over a 10,000 block range from the
`CiphernodeRegistry` deploy block, which contains 125 logs. Provider behaviour changes, so re-run
the commands above rather than trusting this table.

| Endpoint                            | Max `eth_getLogs` range | Archive | Logs returned | Usable                 |
| ----------------------------------- | ----------------------- | ------- | ------------- | ---------------------- |
| `sepolia.gateway.tenderly.co`       | 10,000+                 | Yes     | 125           | Yes                    |
| `ethereum-sepolia-rpc.publicnode.com` | 10,000                | No      | **0**         | No, silent history loss |
| `sepolia.drpc.org`                  | rejected                | No      | —             | No                     |
| `1rpc.io/sepolia`                   | 1                       | No      | —             | No                     |

`publicnode` is the case to understand: it accepts the full 10,000 block range and answers
without an error, yet returns none of the 125 logs. An endpoint can look healthy and still be
unusable.

## Paid providers

Any archive tier works. The whole first sync is a few hundred `eth_getLogs` calls, then one
WebSocket subscription and occasional reads, so cost is not usually the deciding factor.

Check the **free** tier of a paid provider before using it: free tiers often cap `eth_getLogs` to
a much smaller range and may not serve archive state. A small range cap only makes the sync
slower, but missing archive state makes the endpoint unusable.

## Watching a sync

Run the node with `-v` to see each range it requests:

```
Fetched log chunk chain_id=11155111 chunk=1 total_chunks=4 from=11677109 to=11687108 events=125
```

If a provider refuses a range, the node says so and continues with a smaller one:

```
Provider rejected the block range, narrowing the window and retrying chain_id=11155111
  chunk=1 from=11677109 rejected_to=11687108 window=5000 shrinks=1 error=...
```

A window of 128 blocks or fewer is reported separately, because a sync at that width needs many
more requests:

```
The provider caps eth_getLogs to a narrow range. The first sync needs many requests and is
slow. Use an endpoint with a wider range limit to sync faster.
```

Use `-vv` to see the RPC calls themselves. Note that `-vv` prints the full endpoint URL,
including any API key in it, to both the terminal and the log file, so redact before sharing.

## If the node exits during the first sync

- **`429` or "rate limit"**: the node retries these by itself. If it still exits, the endpoint's
  limit is below what a sync needs; use another endpoint. Under systemd, set `Restart=always`
  and `StartLimitIntervalSec=0`, because sync progress is saved and a restart resumes.
- **An error naming a block range**: the node narrows its range by itself, so an exit here means
  the message was not recognised. Report it with the exact provider wording.
- **A sync that completes but the node is never selected**: check the archive command above. This
  is the symptom of a pruned endpoint.
