# Migrating a Ciphernode

This guide moves a running ciphernode to a different server without changing its identity. The
operator address keeps the bond, the peer id keeps existing connections, and the event log keeps the
node from re-syncing the whole chain.

No on-chain action is needed. Bonding follows the operator address, which does not change, so the
registry needs no update.

For a release change, follow the [upgrade procedure](/ciphernode-operators/upgrades) instead. If you
are doing both, migrate first, verify, then upgrade.

## What identifies a node

A ciphernode has three durable pieces, in two directories:

| Item                            | Location                                 | Lost if not copied                    |
| ------------------------------- | ---------------------------------------- | ------------------------------------- |
| Cipher key file                 | `.interfold/config/<node>/key`           | Nothing decrypts; identity unreadable |
| Operator key and libp2p keypair | inside `.interfold/data/<node>/db`       | Bonded identity and peer id           |
| Event history                   | `.interfold/data/<node>/log.<aggregate>` | Full re-sync from each `deploy_block` |

Both keys live **inside the key/value store**, encrypted with the cipher from the key file. Copying
only the data directory therefore produces `Failed to get metadata for keyfile`, and copying only
the config directory leaves nothing to decrypt. The two directories must travel together.

The libp2p keypair is derived from the operator private key, so the peer id follows the operator key
and is not separately generated. A node re-keyed with the same operator key reports the same peer
id.

## Before you start

You need the node's **encryption password**. The key file is derived from it, and there is no
recovery path without it.

Keep the old server's data until the new one is verified and running.

## Procedure

### 1. Stop the old node

Stop the node with whatever supervises it: a service manager, a process manager, a container
runtime, or the terminal it runs in. What matters is that the process exits, which releases its
exclusive lock on the data directory.

```bash
# examples; use whatever runs your node
systemctl stop <unit>
pm2 stop <node>
docker stop <container>
```

Confirm the process is gone before copying:

```bash
interfold node validate --name <node>
```

The command takes the same lock the node holds, so it fails while a node still runs.

The key/value store is not safe to copy while a node writes to it. A copy taken from a running node
can open successfully and still be inconsistent.

### 2. Record what the new server must reproduce

```bash
interfold wallet get      --name <node>
interfold net get-peer-id --name <node>
interfold node validate   --name <node>
```

Write down the address and peer id. The validation report also gives the event count, which is a
useful second check after the move.

### 3. Archive both directories

```bash
tar czpf node-migration.tgz \
  .interfold/config \
  .interfold/data \
  interfold.config.yaml
```

Run this from the directory holding `interfold.config.yaml`. The `p` flag preserves the key file
permissions.

Transfer the archive over a channel you trust. It contains the encrypted operator key.

### 4. Unpack on the new server

Install the same Interfold release first, then unpack in the same relative location:

```bash
tar xzpf node-migration.tgz
```

If the new server uses different paths, keep `interfold.config.yaml` at the root of the node
directory so the `.interfold/` tree is found beside it.

### 5. Verify before starting

```bash
interfold wallet get      --name <node>   # must match the recorded address
interfold net get-peer-id --name <node>   # must match the recorded peer id
interfold node validate   --name <node>   # expect VALIDATION PASSED
```

`node validate` reads the event log and reports a corrupt or truncated copy, so it catches an
incomplete transfer before the node joins the network. Do not start the node until all three agree
with what you recorded.

### 6. Start the new node, then decommission the old one

Start the node the same way you run it elsewhere. Interfold does not require a particular service
manager.

Update the peer list on any node that reaches this one by address. The peer id is unchanged, but a
new IP or port needs a new multiaddr.

## Do not run both servers

Two processes sharing one operator address and one peer id is equivocation. The protocol treats the
conflicting messages as misbehavior, and the bond is at risk. Keep the old node stopped from step 1
until it is decommissioned.

## Notes

- `interfold.lock` in the data directory is an operating-system advisory lock. Copying it is
  harmless; it is released when the process exits.
- `ciphernode.jsonl` is the operational log. Copy it to keep the diagnostic history, or leave it
  behind. It is never read by the node.
- Changing the node name changes the directory layout. Keep `--name` identical, or move the `<node>`
  directories to match the new name in both `config` and `data`.

## Migrating and upgrading together

An incompatible release requires clearing the durable state, which discards the event history a
migration preserves. Do them in this order:

1. Migrate as above and verify the address and peer id on the new server.
2. Follow the [upgrade procedure](/ciphernode-operators/upgrades), including
   `interfold node reset-data`.

Verifying before the reset proves the identity arrived intact. `reset-data` preserves that identity
while clearing the incompatible state, so the node keeps its bond and peer id and re-syncs from each
contract `deploy_block`.

This order matters when the operator key was generated by the node rather than imported. There is no
command that exports a private key, so for such a node the archive is the only copy of that
identity: verify it on the new server before anything deletes state.
