# Running a Ciphernode

This guide covers three methods to run a ciphernode, from easiest to most flexible. Choose the
method that best fits your infrastructure.

For a release change, follow the [ciphernode upgrade procedure](/ciphernode-operators/upgrades).

## Method 1: DAppNode (Easiest)

DAppNode provides a user-friendly interface for running a ciphernode with minimal configuration.

### Installation

1. Open your DAppNode UI (`http://my.dappnode`)
2. Search for **"Interfold Ciphernode"** (the current package name for the Interfold ciphernode) and
   install the package
3. The setup wizard will prompt you for:
   - `RPC_URL` - WebSocket RPC endpoint
   - `NETWORK` and `CHAIN_ID`
   - Contract addresses and deploy blocks
   - Ciphernode credentials JSON file
   - Optional bootstrap peers

4. Confirm and complete the installation
5. Check **Packages → interfold-ciphernode → Logs** to verify the node started

### Configuration via Environment Variables

| Variable                           | Description                                  | Required |
| ---------------------------------- | -------------------------------------------- | -------- |
| `RPC_URL`                          | WebSocket RPC endpoint                       | Yes      |
| `NETWORK`                          | Network name (mainnet, sepolia, etc.)        | Yes      |
| `CHAIN_ID`                         | EIP-155 chain ID                             | Yes      |
| `NODE_ADDRESS`                     | Your Ethereum address                        | Yes      |
| `INTERFOLD_CONTRACT`               | Interfold coordinator contract               | Yes      |
| `CIPHERNODE_REGISTRY_CONTRACT`     | Ciphernode registry contract                 | Yes      |
| `BONDING_REGISTRY_CONTRACT`        | Bonding registry contract                    | Yes      |
| `SLASHING_MANAGER_CONTRACT`        | Slashing manager contract                    | Yes      |
| `FEE_TOKEN_CONTRACT`               | Fee token contract                           | Yes      |
| `INTERFOLD_DEPLOY_BLOCK`           | Interfold contract deploy block              | Yes      |
| `CIPHERNODE_REGISTRY_DEPLOY_BLOCK` | Ciphernode registry deploy block             | Yes      |
| `BONDING_REGISTRY_DEPLOY_BLOCK`    | Bonding registry deploy block                | Yes      |
| `SLASHING_MANAGER_DEPLOY_BLOCK`    | Slashing manager deploy block                | Yes      |
| `FEE_TOKEN_DEPLOY_BLOCK`           | Fee token deploy block                       | Yes      |
| `QUIC_PORT`                        | UDP port for P2P networking (default: 37173) | No       |
| `PEERS`                            | Comma-separated peer multiaddresses          | No       |

Upload the credentials JSON file through the DAppNode setup wizard. The package copies it to
`/run/secrets/secrets.json` before startup.

## Method 2: Interfold CLI (Recommended)

The Interfold CLI provides the most control and is recommended for production deployments.

### Install the CLI

```bash
# Quick install
curl -fsSL https://raw.githubusercontent.com/theinterfold/interfold/main/install | bash

# Then install the CLI
interfoldup install
```

### Initialize Configuration

```bash
interfold ciphernode setup
```

This creates `~/.config/interfold/interfold.config.yaml`. You'll be prompted for a password to
encrypt sensitive data.

### Set Up Credentials

```bash
# Set encryption password (encrypts local keystore)
interfold password set

# Generate or set network keypair (for libp2p)
interfold net keypair generate
# Or import an existing key:
# interfold net keypair set --net-keypair 0x...

# Set your wallet private key (for on-chain transactions)
interfold wallet set --private-key 0xYourPrivateKey
```

### Configure Your Node

Edit `~/.config/interfold/interfold.config.yaml`:

```yaml
node:
  network: mainnet
  address: '0xYourAddress'
  quic_port: 9091
  autonetkey: true
  autopassword: true
  multithread_reserve_threads: 2
  multithread_concurrent_jobs: 2

chains:
  - name: mainnet
    rpc_url: 'wss://eth-mainnet.g.alchemy.com/v2/YOUR_KEY'
    chain_id: 1
    data_availability:
      mode: avail
      rpc_url: 'https://mainnet-rpc.avail.so/rpc'
    contracts:
      interfold:
        address: '0x28cF63B459e6218C69EA97ea7D90541cf648c715'
        deploy_block: 25786382
      ciphernode_registry:
        address: '0xC927A5B2d8F68697bC28C0670df05178c93df2d7'
        deploy_block: 25786378
      bonding_registry:
        address: '0x0ec90465095C21830BEcED07e032809A2Bd2915F'
        deploy_block: 25473398
      slashing_manager:
        address: '0x753109Ee36Dc65cC178875AddA30C6433e5bEEe4'
        deploy_block: 25998899
      fee_token:
        address: '0xdC035D45d973E3EC169d2276DDab16f1e407384F'
        deploy_block: 20663730

  - name: sepolia
    enabled: false
    rpc_url: 'wss://ethereum-sepolia-rpc.publicnode.com'
    chain_id: 11155111
    data_availability:
      mode: avail
      rpc_url: 'https://turing-rpc.avail.so/rpc'
    contracts:
      interfold:
        address: '0x3E856E24c7a95d0e04d387f847DA6FA9f6F6c20C'
        deploy_block: 11534993
      ciphernode_registry:
        address: '0x374F4542eC634d5437Dd65020781A9D9Df9c2AB8'
        deploy_block: 11534965
      bonding_registry:
        address: '0x90250Dc48CBe109fFaA02AeAFbFBdbF12D7BD4d4'
        deploy_block: 11534966
      slashing_manager:
        address: '0x489FB674B143E48eaCAaC999B3DF9EA6E95eA79f'
        deploy_block: 11534963
      fee_token:
        address: '0xC35B783cA97710be47Fc81D10dADc895EfcD865c'
        deploy_block: 11534960
      faucet:
        address: '0x6e281411C055BEEbD74bDFcB9aB095aa98907F85'
        deploy_block: 11534982
```

The compute scheduler defaults to these `2/2` values. It can reduce concurrent jobs when the
detected host or cgroup memory limit is too small. Each secure prover job has a 13 GiB admission
budget, and the scheduler reserves 4 GiB for the node and host. The node refuses to start when the
detected limit cannot cover the node reserve and one prover budget. Do not increase the job count
unless the host has enough memory for all node processes.

If local proof work fails because of memory or another worker error, the node retries it with
backoff and uses Barretenberg low-memory mode after the first failure. A warning that says automatic
recovery remains active is not a failed E3. The node stops those retries when it observes a terminal
E3 event. A non-retryable local error is logged as an error and leaves the durable work available
for repair and restart; it does not accuse another committee member.

Use one coherent provider for the WebSocket subscription and its RPC requests. Do not place a
round-robin pool of independently synchronized providers behind one local URL. A subscription can
announce a block before another pool member can return that block or its logs.

Chain ingestion waits for one confirmation by default. This default also applies when `rpc_url` uses
`localhost` or `127.0.0.1`, because that URL can be a proxy to a live chain. Set
`ingestion_confirmations: 0` only for a single-process development chain such as Anvil. Do not set
it to zero for Mainnet or Sepolia.

### Check Your Addresses Are Current

Contract addresses change when the protocol is redeployed, and a node pointed at an old address
fails silently — it syncs nothing and reports no error. Before starting, and after any redeploy
announcement, compare your config against the published deployment manifest:

```bash
interfold config check
```

```
Deployment manifest: release v0.12.1
sepolia:
  STALE interfold: config has 0x38A8A686…, published is 0x3E856E24…
  warn  ciphernode_registry: deploy_block 11508403, published is 11534965
```

The command exits non-zero when any address is wrong, so it can gate a restart in a supervisor or a
CI job. A stale `deploy_block` or an unconfigured optional contract is reported but does not fail
the check. Use `--chain <name>` to check a single chain, and `--manifest-url <url>` to check against
a specific manifest instead of the latest release.

### Start Your Node

```bash
# Start in foreground with verbose logging
interfold start -v

# Or use the node supervisor for multiple nodes
interfold nodes up --detach
interfold nodes ps          # Check status
interfold nodes logs cn1    # View logs
interfold nodes down        # Stop all nodes
```

## Method 3: Docker

For containerized deployments, you can run the ciphernode Docker image directly.

### Pull the Image

Pull and run an explicit versioned release tag for an operator node. Do not use the mutable `latest`
tag:

```bash
export CIPHERNODE_IMAGE='ghcr.io/theinterfold/ciphernode:<release-version>'
docker pull "$CIPHERNODE_IMAGE"
```

### Create Configuration

Create a `config.yaml` file:

```yaml
node:
  network: sepolia
  address: '0xYourAddress'
  quic_port: 9091
  autonetkey: true

chains:
  - name: sepolia
    rpc_url: 'wss://ethereum-sepolia-rpc.publicnode.com'
    chain_id: 11155111
    contracts:
      interfold:
        address: '0x3E856E24c7a95d0e04d387f847DA6FA9f6F6c20C'
        deploy_block: 11534993
      ciphernode_registry:
        address: '0x374F4542eC634d5437Dd65020781A9D9Df9c2AB8'
        deploy_block: 11534965
      bonding_registry:
        address: '0x90250Dc48CBe109fFaA02AeAFbFBdbF12D7BD4d4'
        deploy_block: 11534966
      slashing_manager:
        address: '0x489FB674B143E48eaCAaC999B3DF9EA6E95eA79f'
        deploy_block: 11534963
      fee_token:
        address: '0xC35B783cA97710be47Fc81D10dADc895EfcD865c'
        deploy_block: 11534960
      faucet:
        address: '0x6e281411C055BEEbD74bDFcB9aB095aa98907F85'
        deploy_block: 11534982
```

### Create the Credentials Secret

On the first boot, the image entrypoint requires a JSON secret mounted at
`/run/secrets/secrets.json`. It does not read wallet credentials from `PRIVATE_KEY` or
`ENCRYPTION_PASSWORD` environment variables. Create this file on the host with restrictive
permissions; do not commit it, paste it into shell history, or reuse the example/development keys
from the repository:

```bash
umask 077
install -m 600 /dev/null secrets.json
${EDITOR:-vi} secrets.json
```

```json
{
  "password": "<strong-key-encryption-password>",
  "private_key": "<operator-wallet-private-key>"
}
```

Both values are required. The wallet command derives the libp2p identity from the operator wallet
key. Back up the encrypted node data and this password through your secret-management system. Keep
the wallet key in the project-approved signing system.

The entrypoint reads this file only when the volume has no key file or no wallet key. After it uses
the file, it tries to delete it. A read-only mount stays in place, and the boot continues.

Do not set `autopassword` in `config.yaml` for the image. With `autopassword`, the node creates a
random password before the entrypoint can set the password from this file.

### Run the Container

```bash
docker run -d \
  --name ciphernode \
  --restart unless-stopped \
  --stop-timeout 300 \
  -v $(pwd)/config.yaml:/home/ciphernode/.config/interfold/config.yaml:ro \
  -v $(pwd)/secrets.json:/run/secrets/secrets.json:ro \
  -v ciphernode-data:/home/ciphernode/.local/share/interfold \
  -p 9091:9091/udp \
  "$CIPHERNODE_IMAGE"
```

### Docker Compose

For a more manageable setup, use Docker Compose:

```yaml
services:
  ciphernode:
    image: ${CIPHERNODE_IMAGE:?CIPHERNODE_IMAGE-must-use-a-versioned-release-tag}
    restart: unless-stopped
    stop_grace_period: 5m
    volumes:
      - ./config.yaml:/home/ciphernode/.config/interfold/config.yaml:ro
      - ciphernode-data:/home/ciphernode/.local/share/interfold
    secrets:
      - source: ciphernode_credentials
        target: secrets.json
    ports:
      - '9091:9091/udp'

secrets:
  ciphernode_credentials:
    file: ./secrets.json

volumes:
  ciphernode-data:
```

Before starting after a crash, restore, or binary upgrade, keep the container stopped and run the
same release's offline integrity check against the mounted configuration and data:

```bash
docker run --rm \
  -v $(pwd)/config.yaml:/home/ciphernode/.config/interfold/config.yaml:ro \
  -v ciphernode-data:/home/ciphernode/.local/share/interfold \
  "$CIPHERNODE_IMAGE" \
  node validate --config /home/ciphernode/.config/interfold/config.yaml
```

Do not start the node when validation reports `FAIL`; preserve a copy of the volume before repair,
restore, or controlled resynchronization.

If validation reports only a recoverable uncommitted event-log tail, or a stale sortition projection
while the event log, schema, and snapshot cursor checks all pass, keep the node stopped and run the
same command with `--repair`. This repair can re-index complete uncommitted frames, truncate a torn
physical suffix, or rebuild the derived sortition projection from intact events. It never removes an
indexed event and cannot repair committed corruption or an unsupported storage schema.

### Where the Node Stores Its State

The image sets `E3_CONFIG_DIR=/home/ciphernode/.local/share/interfold/config` and
`E3_DATA_DIR=/home/ciphernode/.local/share/interfold/data`. Thus the node keeps all of its state on
the volume at `/home/ciphernode/.local/share/interfold`:

| Path on the volume    | Contents                                                                        |
| --------------------- | ------------------------------------------------------------------------------- |
| `config/_default/key` | Key file with the password that encrypts the stored keys                        |
| `data/_default/db`    | Key/value store: wallet key, libp2p keypair, key shares, and protocol snapshots |
| `data/_default/log.*` | Event logs                                                                      |

A restart, a new container, and a new image all keep this state. `docker rm` does not delete a named
volume.

These variables override `config.yaml`, so the entrypoint never uses them to move state that exists.
If `config.yaml` sets `config_dir`, `data_dir`, `key_file`, or `db_file`, the node uses that
location. If a key file or database exists at the location that earlier images used, for example on
a directory that is mounted there, the node keeps using it. If state exists both there and on the
volume, the container does not start. Keep only the state that the node last used, and start the
container again. You can also set your own `E3_CONFIG_DIR` and `E3_DATA_DIR` for the container.

In these cases the node does not use the image variables, so run other `interfold` commands through
the entrypoint, which chooses the same location. For example, run
`docker exec ciphernode ciphernode-entrypoint.sh wallet get --config /home/ciphernode/.config/interfold/config.yaml`.
The validation command above also runs through the entrypoint.

### Move State from an Earlier Image

Earlier images did not set these variables. A node that started from such an image keeps its state
inside the container, in `/home/ciphernode/.config/interfold/.interfold`. That directory is not on
the volume. When you remove or recreate that container, you lose the key file, the key/value store,
and the event log. The key/value store holds the key shares of the node, and the chain cannot
restore them.

> **Warning:** Do not remove or recreate the old container before you copy its state. `docker rm`,
> `docker compose down`, and `docker compose up` with a new image all remove the old container.
> Never do this migration with `interfold node reset-data` or `interfold nodes purge`. These
> commands delete the state that you must keep.

Do this procedure one time for each node. Do it only when the new image accepts the stored schema. A
node that serves an active E3 on v0.17.0 must stay on v0.17.0. See
[Upgrade a node that serves an active E3](/ciphernode-operators/upgrades#upgrade-a-node-that-serves-an-active-e3).

The commands use the container name `ciphernode` and the volume name `ciphernode-data`. For Docker
Compose, use the names that `docker ps -a` and `docker volume ls` show.

1. Stop the old container. Do not remove it.

   ```bash
   docker stop --time 300 ciphernode
   ```

2. Make sure that the volume has no `data` or `config` directory. If the output shows either name,
   stop and contact the protocol team.

   ```bash
   docker run --rm \
     -v ciphernode-data:/home/ciphernode/.local/share/interfold \
     --entrypoint ls \
     "$CIPHERNODE_IMAGE" \
     -A /home/ciphernode/.local/share/interfold
   ```

3. Copy the `data` and `config` directories from the old container to the volume. `docker cp` sends
   each directory as a tar stream, so the key file does not go to the host disk.

   ```bash
   for dir in data config; do
     docker cp "ciphernode:/home/ciphernode/.config/interfold/.interfold/$dir" - |
       docker run --rm -i \
         -v ciphernode-data:/home/ciphernode/.local/share/interfold \
         --entrypoint tar \
         "$CIPHERNODE_IMAGE" \
         -xf - -C /home/ciphernode/.local/share/interfold
   done
   ```

4. Make sure that the copy is complete. The output must show `key`, `db`, and `log.0`. If a name is
   missing, stop and contact the protocol team.

   ```bash
   docker run --rm \
     -v ciphernode-data:/home/ciphernode/.local/share/interfold \
     --entrypoint ls \
     "$CIPHERNODE_IMAGE" \
     /home/ciphernode/.local/share/interfold/config/_default \
     /home/ciphernode/.local/share/interfold/data/_default
   ```

5. Run the offline validation command from [Docker Compose](#docker-compose) with the new image.
   Continue only if the report shows `on-disk schema version 7 matches this binary` and ends with
   `VALIDATION PASSED — state is intact and consistent.` If validation fails, or if it shows
   `empty store will be initialized`, do not start the new image. Keep the old container and the
   volume, and contact the protocol team.

6. Start the new image. For `docker run`, rename the old container first, then use the command in
   [Run the Container](#run-the-container):

   ```bash
   docker rename ciphernode ciphernode-old
   ```

   For Docker Compose, set the new image and run `docker compose up -d`. This command replaces the
   old container.

7. Make sure that the log shows `Ciphernode release is accepted`, and that this command shows the
   operator address:

   ```bash
   docker exec ciphernode ciphernode-entrypoint.sh wallet get --config /home/ciphernode/.config/interfold/config.yaml
   ```

8. For `docker run`, remove the old container only after step 7 succeeds.

### Persistent Event Data

The node's append-only event log is its durable source of truth. Events below the 32 MiB framed
commit-log limit stay inline. Larger local events, including proof work plans, are stored as
content-addressed files in an `event-blobs-v1` directory inside the event-log directory. Each blob
is limited to 512 MiB. The node checks its recorded length and SHA-256 hash whenever it opens the
log.

Startup removes only orphan blob files that have no committed event-log reference. A blob referenced
by protocol history remains part of the node's durable state after an E3 completes. Back up the full
data volume, including `event-blobs-v1`, and monitor disk growth. Do not delete individual blob
files to reclaim space; that makes the referenced event history unreadable.

An unrecoverable event-log write or flush failure stops the node so its supervisor can restart it.
Treat repeated storage failures as an infrastructure incident. Stop the node, preserve the volume,
and run the offline validator before another restart.

### View Logs

```bash
docker logs -f ciphernode
```

## Configuration Reference

### Node Configuration

| Field          | Description                                    | Default                    |
| -------------- | ---------------------------------------------- | -------------------------- |
| `network`      | P2P profile: `mainnet`, `sepolia`, or `local`  | Inferred from chain ID     |
| `network_id`   | Stable 32-byte hex ID for a custom P2P network | Required for custom names  |
| `address`      | Your Ethereum address                          | Required                   |
| `quic_port`    | UDP port for QUIC/libp2p networking            | `9091`                     |
| `peers`        | Explicit bootstrap overrides                   | Profile DNS bootstrap      |
| `autopassword` | Auto-generate password if missing              | `false`                    |
| `autowallet`   | Auto-load wallet from environment              | `false`                    |
| `data_dir`     | Override data directory                        | `~/.local/share/interfold` |
| `config_dir`   | Override config directory                      | `~/.config/interfold`      |

### Chain Configuration

| Field       | Description                          | Required |
| ----------- | ------------------------------------ | -------- |
| `name`      | Chain identifier                     | Yes      |
| `rpc_url`   | WebSocket RPC endpoint               | Yes      |
| `chain_id`  | EIP-155 chain ID                     | No       |
| `contracts` | Contract addresses and deploy blocks | Yes      |

Set `chain_id` even though it is optional: `interfold config check` compares it against the manifest
rather than querying the endpoint, so it is the only thing that catches an `rpc_url` pointing at the
wrong network. Without it, a config whose addresses all match but whose RPC points elsewhere passes
the check.

### Contract Addresses

Each chain requires these contract addresses:

| Contract              | Description                          | Required for ciphernode |
| --------------------- | ------------------------------------ | ----------------------- |
| `interfold`           | Main Interfold coordinator contract  | Yes                     |
| `ciphernode_registry` | Tracks registered operators          | Yes                     |
| `bonding_registry`    | Manages bonds and tickets            | Yes                     |
| `slashing_manager`    | Manages slashing penalties           | Yes                     |
| `e3_program`          | E3 Program contract address          | No                      |
| `fee_token`           | Fee token address for E3 requests    | No                      |
| `faucet`              | Testnet faucet for FOLD + fee tokens | No                      |

Each contract can be specified as a simple address string or with a deploy block for faster syncing:

```yaml
contracts:
  interfold:
    address: '0x3E856E24c7a95d0e04d387f847DA6FA9f6F6c20C'
    deploy_block: 11534993
  ciphernode_registry: '0x374F4542eC634d5437Dd65020781A9D9Df9c2AB8'
  faucet:
    address: '0x6e281411C055BEEbD74bDFcB9aB095aa98907F85'
    deploy_block: 11534982
```

## Networking Requirements

### Firewall Configuration

Open the following ports:

| Port   | Protocol | Purpose                    |
| ------ | -------- | -------------------------- |
| `9091` | UDP      | QUIC/libp2p P2P networking |

> **Important:** Port `50505` (TCP) is used for local CLI commands and binds to `localhost` only.
> **Do not expose this port externally** - it provides control plane access to your node.

### Bootstrap Peers

Set the network profile and omit `peers` to use its DNS bootstrap address:

```yaml
node:
  network: mainnet
```

Mainnet uses `/dnsaddr/bootstrap.interfold.network`. Sepolia uses
`/dnsaddr/bootstrap-sepolia.interfold.network`. The profile scopes every libp2p protocol, so a node
cannot join the other network even if DNS or an explicit peer address is wrong.

Or specify individual peers:

```yaml
node:
  network: mainnet
  peers:
    - '/dns4/node1.example.com/udp/9091/quic-v1'
    - '/ip4/192.168.1.100/udp/9091/quic-v1'
```

## Data Directories

| Directory                        | Contents                          |
| -------------------------------- | --------------------------------- |
| `~/.config/interfold/`           | Configuration files, network keys |
| `~/.local/share/interfold/`      | Databases, job data, keystores    |
| `~/.local/share/interfold/jobs/` | Per-E3 secret shares and state    |

> Back up these directories regularly. The `jobs/` directory contains encrypted key shares for
> active E3s - losing this data while participating in a committee may result in slashing.

| Event                       | Meaning                               |

| `E3Requested`               | New computation request detected      |
