# Ciphernode Upgrades

Interfold checks each ciphernode release against an on-chain governance policy before the node
starts protocol actors. An outdated node fails startup and cannot become an active operator.

## What the versions mean

| Value            | Increase it when                                                          |
| ---------------- | ------------------------------------------------------------------------- |
| Release ID       | The exact release version changes                                         |
| Protocol version | Contracts, events, cryptography, or protocol behavior become incompatible |
| Node generation  | A node-only fix must be installed by every operator                       |

The release ID records the exact binary version, but it does not control eligibility. Compatible
releases keep both compatibility values and need no governance transaction. A compatible
contract-only fix also needs no node policy change.

The P2P network also includes the protocol version in its gossip, discovery, and synchronization
names. Nodes on incompatible protocol versions reject each other. Compatible patch releases use the
same protocol version and stay connected.

Treat a node bug that affects network parsing, message meaning, or peer safety as an incompatible
protocol change. A node-generation cutover excludes stale nodes from new committees, but it does not
place otherwise compatible releases on separate P2P networks.

## Compatible rolling release

Operators can install a backward-compatible release at their own pace. Both old and new releases can
participate because they report the same compatibility values. Restart one operator at a time and
keep enough current committee members online to retain the threshold.

## Mandatory release

For a security fix or incompatible change, governance uses a clean cutover:

1. Pause new E3 requests.
2. Wait for all active E3s and committee obligations to finish.
3. Raise the required compatibility value.
4. Upgrade at least one configured bootstrap peer.
5. Restart every ciphernode with the new release.
6. Wait until enough upgraded nodes are active to fill the largest committee and can discover one
   another.
7. Resume requests.

Raising the requirement immediately marks every previous operator status inactive. The new binary
checks the policy, acknowledges its release on-chain, and refreshes its operator status during
startup. Old nodes cannot enter new committees, so they cannot hold a new computation hostage.

## Operator procedure

Keep the node stopped, pull the exact versioned image, run the offline validation command from the
[running guide](/ciphernode-operators/running#run-the-container), and start the node. A successful
startup log includes `Ciphernode release is accepted`. If the release is below the required value,
leave the node stopped and contact the protocol team.

### Persistent-state compatibility

The current protocol-v4 binary uses storage schema 6. It accepts only an exact schema match because
the event log and actor snapshots contain protocol-bearing binary data. It rejects both older state
and state written by a newer binary instead of guessing that the layouts are compatible.

The protocol-v4 rollout has no automatic migration from earlier pre-release state. Before that
cutover, governance must pause requests and drain active work. Operators must then:

1. Stop the node and preserve a backup of its data volume.
2. Back up the node identity, wallet credentials, configuration, and encryption password separately.
3. Run `interfold node reset-data --name <node> --yes` to clear the incompatible protocol state and
   perform a controlled resync.
4. Run `interfold node validate` with the new binary before starting normal service.

Do not delete identity or signing credentials as part of a state reset. Do not reuse an old state
volume after the binary reports a schema mismatch unless a later release provides an explicit
migration.

### Clearing incompatible state

The wallet key and the libp2p keypair are stored inside the same key/value store as the protocol
state, so deleting the data directory by hand also destroys the operator identity that holds the
bond. `interfold nodes purge` is worse: it also removes the configuration directory, which holds the
encryption key file. Neither is the correct procedure.

`interfold node reset-data` clears exactly the incompatible state and keeps the identity:

```bash
# 1. Stop the node first. The command takes the node's exclusive process fence
#    and refuses while a node is running.
pm2 stop <node>            # or: systemctl stop <unit>

# 2. Clear the state. Both the event log and the key/value store are removed.
interfold node reset-data --name <node> --yes

# 3. Confirm the identity survived. This must print the same operator address
#    as before the reset.
interfold wallet get --name <node>

# 4. Validate the fresh state with the new binary, then start the node.
interfold node validate --name <node>
```

The command copies the operator key and the libp2p keypair out as ciphertext, writes them to a
`0600` backup file next to the data directory, removes the state, then restores and reads them back
to confirm they match. The encryption password is never required, so no key material is decrypted.
The backup file remains after a successful reset; delete it once the node is running.

The event log and the key/value store must be cleared together, which is why the command removes
both. The schema marker lives in the key/value store, so clearing only that leaves an unmarked event
log, and the node halts with `On-disk state has no schema marker` instead of starting.

`--name` is required. Without it the CLI uses the default keyring rather than the node's, and
`interfold wallet get` reports that no wallet has been set.

Use this command only when a release note instructs you to. It is not a general repair tool: a node
that is a member of a live committee loses its keyshare and fails that E3.

To move a node to a different server, see [migrating a ciphernode](/ciphernode-operators/migrating).
Migrate and verify the identity first, then reset.

### Configuration changes this release requires

The protocol-v4 binary retrieves proof-backed ciphertext outputs from a data-availability layer, so
every enabled chain entry that configures the `interfold` contract also needs a `data_availability`
block. A configuration written for an earlier release does not have one, and the node exits after
accepting the release with:

```text
chain 'mainnet' has Interfold enabled but no data_availability reader;
this protocol release must retrieve proof-backed ciphertext outputs
```

Add the block inside the chain entry:

```yaml
chains:
  - name: mainnet
    chain_id: 1
    data_availability:
      mode: avail
      rpc_url: 'https://mainnet-rpc.avail.so/rpc'
```

Use `https://turing-rpc.avail.so/rpc` only for Sepolia. The `mock_http` mode exists for the test
harness and must never be used on a live chain. Make this change while the node is stopped, so the
reset and the configuration fix are both in place before the first start.

`interfold node validate` is read-only by default. `interfold node validate --repair` can repair
only a provably uncommitted event-log tail, such as complete frames whose final index write was
interrupted. It does not repair an indexed corrupt record, an offset mismatch, or an unsupported
schema. Preserve the stopped volume and use a verified backup or controlled resync for those
failures.

Release acknowledgement prevents accidental use of stale software. It is not remote attestation of
the executable. Interfold still relies on threshold cryptography, proof verification, committee
checks, and slashing to handle malicious operators.

The active-operator count proves contract eligibility, not that every process is online or mutually
reachable. Confirm node health and P2P connectivity before governance resumes requests. A mandatory
cutover can also be delayed by an active E3 or unreleased committee because the policy cannot change
until both are terminal.

Required versions never decrease. A rollback uses a new release that raises the applicable value and
never lowers the other value, even when it restores earlier code or contract behavior.
