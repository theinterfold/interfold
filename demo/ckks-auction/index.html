1 Request committee via CKKS program

One on-chain tx. Sortition selects 3 of the 5 registered ciphernode processes; the E3 program's address selects the FHE scheme.

2 Distributed key generation

The 3 selected node processes run the CKKS DKG over libp2p: ephemeral keys → BFV-encrypted dealt Shamir rows → C2-checked broadcast → byte-identical joint public key, published on-chain.

3 Submit encrypted bids

Each bid is a genuine CKKS encryption under the committee's joint pk (fresh randomness, slot-replicated). No party — including the nodes — can read an individual bid.

4 Homomorphic auction round

Leak-free ITERATED SIGN EXTRACTION computed ON the ciphertexts: every i<j pair difference is packed into ONE ciphertext (normalized by the bid cap), then a cubic sign map f(y)=1.5y−0.5y³ is iterated 12× slot-wise (two relinearized ct×ct products per iteration, using the committee's multiparty relin-ceremony keys) until every slot saturates at exactly ±1. One evaluation, ONE threshold opening, and the winner falls out of the dominance matrix. Bid values AND gap magnitudes are never revealed — only ±1 comparison bits ever come out.

5 Threshold decryption & on-chain result

Seeing the ciphertext on-chain, each committee node computes a decryption share (secret share + smudging noise). Any t+1 = 2 shares reconstruct — the aggregator publishes canonical fixed-point bytes via publishPlaintextOutput.
